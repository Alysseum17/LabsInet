# ЧАСТИНА 1. ТЕОРІЯ

## 1.1. Навіщо потрібна NFS

**NFS (Network File System)** дозволяє змонтувати каталог, що фізично лежить на **іншій машині**, так, ніби він локальний. Програми на клієнті працюють із ним звичайними викликами (`open`, `read`, `write`) і не знають, що файли насправді приїжджають по мережі. Створена в компанії Sun Microsystems у 1984 році, зараз це стандарт для Unix/Linux.

Типові застосування: спільні домашні каталоги користувачів на багатьох машинах, спільні дані для кластера, централізоване сховище для віртуалізації.

Порівняй із FTP із ЛР4: у FTP файл **копіюється** на клієнт командою `get`, а в NFS файл **залишається на сервері**, і клієнт читає чи пише його частинами прямо там.

## 1.2. Версії протоколу

| Версія | RFC | Особливості |
|---|---|---|
| NFSv2 | 1094 (1989) | UDP, 32-бітні розміри файлів, **без стану** (stateless) |
| **NFSv3** | 1813 (1995) | UDP/TCP, великі файли, асинхронний запис, **без стану**. Для роботи потрібні окремі служби: `rpcbind`, `mountd`, `statd`, `lockd` |
| **NFSv4** | 3010 → 3530 → **7530** (2015) | **тільки TCP, порт 2049**, **зі станом** (stateful), mount і блокування вбудовані в сам протокол, `rpcbind` і `mountd` не потрібні, є Kerberos, імена користувачів замість голих чисел |
| NFSv4.1 / 4.2 | 5661, 7862 | паралельний доступ (pNFS), серверне копіювання тощо |

Контрольні питання (3.3, 3.4) стосуються `mountd` і `rpcbind`, а вони потрібні саме у **NFSv3**. Тому основні тести робимо з опцією `vers=3`, де видно всі компоненти й весь процес монтування. NFSv4 перевіряємо додатково (Крок 10).

## 1.3. NFS і модель ISO OSI (контрольне питання 3.1)

NFS **не вкладається в один рівень** моделі, а складається з кількох протоколів:

| Рівень OSI | Що відповідає в NFS |
|---|---|
| 7 — Прикладний | **NFS** (операції з файлами: `LOOKUP`, `READ`, `WRITE`...) і **MOUNT** (монтування) |
| 6 — Представлення | **XDR** (eXternal Data Representation, RFC 4506): єдиний формат кодування даних, щоб різні архітектури розуміли одне одного (різний порядок байтів тощо) |
| 5 — Сеансовий | **ONC RPC** (Remote Procedure Call, RFC 5531): виклик процедури на віддаленій машині |
| 4 — Транспортний | **TCP** або **UDP** (v4: лише TCP, порт 2049) |
| 3 — Мережний | IP |

Іншими словами, NFS є **набором процедур, що викликаються через RPC**, а дані в цих викликах кодує XDR.

## 1.4. RPC і XDR

**RPC** схожий на звичайний виклик функції, тільки функція виконується на сервері. Клієнт формує запит: *номер програми* (яка служба), *версія*, *номер процедури* та *аргументи*. Сервер виконує і повертає результат.

Кожна служба має стандартний **номер програми**:

| Номер програми | Служба |
|---|---|
| 100000 | `portmapper` / `rpcbind` |
| 100003 | `nfs` (файлові операції) |
| 100005 | `mountd` (монтування) |
| 100021 | `nlockmgr` / `lockd` (блокування файлів) |
| 100024 | `status` / `statd` (стан клієнтів, відновлення блокувань) |

Номер порту для кожної такої програми може бути **будь-яким** (крім nfs: 2049 і rpcbind: 111). Саме для цього існує `rpcbind` (п. 1.5).

## 1.5. Архітектура NFS і компоненти (контрольні питання 3.2, 3.3)

```
          КЛІЄНТ (VM2)                                  СЕРВЕР (VM1)
   ┌──────────────────────┐                     ┌──────────────────────────┐
   │ програма: ls, cat... │                     │  /etc/exports            │
   │         │            │                     │  (що і кому експортуємо) │
   │   VFS (ядро Linux)   │                     │            │             │
   │         │            │                     │   ┌────────┴───────┐     │
   │   NFS-клієнт (ядро)  │ ── RPC/XDR ──────►  │   │ rpcbind  :111  │     │
   │         │            │                     │   │ mountd   :20048│     │
   │  mount.nfs (nfs-     │                     │   │ nfsd     :2049 │     │
   │  common), rpcbind    │                     │   │ statd, lockd   │     │
   └──────────────────────┘                     │   └────────┬───────┘     │
                                                │   VFS → файлова система  │
                                                │   (ext4, права, ACL)     │
                                                └──────────────────────────┘
```

| Компонент | Де | Що робить |
|---|---|---|
| **`rpcbind`** (portmapper), порт **111** | сервер (і клієнт) | **Довідкова служба.** Ведe таблицю «номер RPC-програми → порт». Клієнт спочатку питає в нього, на якому порту слухає `mountd` або `nfsd`, і лише потім звертається туди. Без `rpcbind` NFSv3 не працює |
| **`mountd`** (`rpc.mountd`), програма 100005 | сервер | **Обробляє запити на монтування.** Читає `/etc/exports`, перевіряє, чи дозволено клієнтові (за IP) цей експорт, і якщо так, повертає **файловий дескриптор (file handle)** кореня експорту. Також веде список змонтованих клієнтів (`showmount -a`) |
| **`nfsd`** (`rpc.nfsd`), програма 100003, порт **2049** | сервер | **Виконує самі файлові операції** (читання, запис, створення, видалення). Працює як набір **потоків ядра** (kernel threads), тому швидкий. Перевіряє права доступу за UID/GID із запиту |
| `statd` (100024) і `lockd` (100021) | обидві сторони | Блокування файлів (`flock`/`fcntl`) і відновлення блокувань після перезавантаження. Нам для лабораторної не потрібні, але видно в `rpcinfo` |
| `idmapd` | v4 | Зіставлення імен користувачів і числових UID (тільки NFSv4) |
| `exportfs` | сервер | Утиліта, що **застосовує** `/etc/exports` до ядра |

Важлива особливість NFSv3: **сервер не зберігає стану**. Кожен запит містить усе необхідне (file handle, зсув, довжина). Тому після перезавантаження сервера клієнти просто продовжують роботу.

## 1.6. Процедура монтування (контрольне питання 3.4)

### NFSv3 (повна процедура з усіма компонентами)

```
Клієнт (VM2)                                      Сервер (VM1)
   │  1. mount nfs.color.edu:/nfs/public /mnt/...      │
   │                                                    │
   │── 2. rpcbind :111: "на якому порту mountd?" ──────►│  PMAP GETPORT(100005, v3)
   │◄───────────────── порт 20048 ─────────────────────│
   │                                                    │
   │── 3. mountd :20048: MNT("/nfs/public") ───────────►│  перевірка /etc/exports
   │◄── статус OK + FILE HANDLE кореня + auth flavors ──│  (чи дозволено IP клієнта)
   │                                                    │
   │── 4. rpcbind :111: "на якому порту nfs?" ─────────►│  (зазвичай 2049)
   │◄───────────────── порт 2049 ──────────────────────│
   │                                                    │
   │── 5. nfsd :2049: GETATTR / FSINFO / ACCESS ───────►│  з file handle з кроку 3
   │◄─────────────────── атрибути ──────────────────────│
   │                                                    │
   │  6. ядро клієнта підключає віддалену ФС до         │
   │     точки монтування /mnt/...                      │
   │                                                    │
   │── далі: LOOKUP, READDIR, READ, WRITE, CREATE ... ─►│  усе на :2049
```

Ключова ідея: **file handle** — це непрозорий «ключ» до каталогу, який видає `mountd`. Усі наступні операції `nfsd` виконує за цим ключем.

### NFSv4 (спрощена)

Клієнт підключається **одразу до порту 2049** і виконує звичайні операції протоколу (`PUTROOTFH`, `LOOKUP`, `GETFH`...). Окремих `rpcbind` і `mountd` немає. Через це NFSv4 значно простіше проходить через файрволи.

## 1.7. Автентифікація, UID і «squash» (ключове для варіанту 6)

Звичайна NFS (режим `sec=sys`, він же `AUTH_SYS`) **не перевіряє пароль користувача**. Клієнт просто пише в кожному RPC-запиті **числові UID і GID** свого користувача, а сервер їм **довіряє** і застосовує звичайні права файлової системи за цими числами.

З цього випливають два важливі наслідки:

1. **UID мають збігатися на клієнті й сервері.** Якщо на клієнті `blue` має UID 1003, а на сервері UID 1003 належить `blue`, то права працюють «за іменем». Якщо UID різні, сервер бачить чужу людину. Тому в Кроці 1 ми створимо на VM2 користувачів з **тими самими UID**, що й на VM1.
2. **Довіряти root клієнта небезпечно:** будь-хто з root на клієнті міг би підставити будь-який UID, включно з UID власника файлів. Тому існують правила **відображення (squash)**:

| Опція в `/etc/exports` | Що робить |
|---|---|
| `root_squash` (**за замовчуванням**) | запити від **root (UID 0)** клієнта відображаються на «анонімного» користувача (за замовчуванням `nobody`). Інші користувачі залишаються **без змін** |
| `no_root_squash` | root клієнта лишається root і на сервері (небезпечно) |
| `all_squash` | **усі** користувачі клієнта (і root теж) відображаються на анонімного |
| `anonuid=N`, `anongid=N` | **на кого саме** відображати: замість `nobody` буде користувач із UID `N` і GID `N` |

Звідси два наших експорти:

| Експорт | Опції | Що відбувається |
|---|---|---|
| `/nfs/private` | `all_squash,anonuid=red,anongid=red` | **усі** на клієнті (root, blue, white... будь-хто) стають `red` на сервері. Власник каталогу `red`, тому всі отримують повні права |
| `/nfs/incoming` | `root_squash,anonuid=green,anongid=green` (без `all_squash`) | **root** клієнта стає `green`, а **звичайні користувачі лишаються собою** (`blue` лишається `blue`). Права вирішує ACL каталогу |

## 1.8. Файл `/etc/exports`

Кожен рядок описує один експорт:

```
/шлях/до/каталогу   клієнт1(опції)   клієнт2(опції)
```

**Як задавати клієнтів:**

| Запис | Значення |
|---|---|
| `192.168.106.20` | один конкретний вузол |
| `192.168.106.0/24` | усі вузли мережі |
| `nfs-client.color.edu` | за доменним іменем |
| `*` | будь-хто (для лабораторної не використовуємо) |

**Основні опції:**

| Опція | Значення |
|---|---|
| `ro` / `rw` | тільки читання / читання і запис |
| `sync` | сервер відповідає клієнту **лише після** того, як дані справді записані на диск (надійно). Протилежна `async` швидша, але при збої можна втратити дані |
| `no_subtree_check` | не перевіряти, чи файл лежить усередині експортованого піддерева. Дрібна перевірка, що тільки створює проблеми, рекомендовано вимикати |
| `root_squash`, `no_root_squash`, `all_squash` | див. п. 1.7 |
| `anonuid`, `anongid` | кого вважати «анонімом» |
| `secure` (за замовч.) | приймати запити лише з привілейованих портів (<1024) клієнта |

> Між іменем клієнта і дужкою **не має бути пробілу**: `192.168.106.20(rw)` — вірно, `192.168.106.20 (rw)` означає зовсім інше (опції `rw` для **всіх**, а клієнту без опцій).

## Крок 1. Користувачі та їхні UID (на VM1 і VM2)

NFS (див. п. 1.7) передає **числа**, а не імена. Тому `red`, `green`, `blue`, `black`, `white` мусять мати **однакові UID/GID на обох машинах**.

### 1.1. VM1: подивитися, які UID уже є

Ці користувачі створювалися в ЛР4 (FTP). Перевір:

```bash
for u in red green blue black white; do id $u; done
```

Очікувано щось на кшталт (числа в тебе можуть бути іншими):

```
uid=1001(red) gid=1001(red) groups=1001(red)
uid=1002(green) gid=1002(green) groups=1002(green)
uid=1003(blue) gid=1003(blue) groups=1003(blue)
uid=1004(black) gid=1004(black) groups=1004(black)
uid=1005(white) gid=1005(white) groups=1005(white)
```

Далі в інструкції я використовую саме ці значення. **Якщо в тебе інші, скрізь підстав свої.**

Якщо когось ще немає, створи (UID задаємо явно):

```bash
sudo groupadd -g 1001 red   && sudo useradd -m -u 1001 -g 1001 -s /usr/sbin/nologin red
sudo groupadd -g 1002 green && sudo useradd -m -u 1002 -g 1002 -s /usr/sbin/nologin green
sudo groupadd -g 1003 blue  && sudo useradd -m -u 1003 -g 1003 -s /usr/sbin/nologin blue
sudo groupadd -g 1004 black && sudo useradd -m -u 1004 -g 1004 -s /usr/sbin/nologin black
sudo groupadd -g 1005 white && sudo useradd -m -u 1005 -g 1005 -s /usr/sbin/nologin white
```

| Частина | Що означає |
|---|---|
| `groupadd -g 1001 red` | створити групу `red` з GID 1001 |
| `useradd -m` | створити домашній каталог |
| `-u 1001` | **явний UID** |
| `-g 1001` | основна група з GID 1001 |
| `-s /usr/sbin/nologin` | вхід у систему заборонено; акаунт потрібен лише як власник файлів |

### 1.2. VM2: ті самі користувачі з тими самими UID

Спершу перевір, що ці числа вільні:

```bash
getent passwd 1001 1002 1003 1004 1005
```

Порожній вивід означає, що вільні. Далі створи тих самих користувачів (UID/GID як на VM1):

```bash
sudo groupadd -g 1001 red   && sudo useradd -m -u 1001 -g 1001 -s /usr/sbin/nologin red
sudo groupadd -g 1002 green && sudo useradd -m -u 1002 -g 1002 -s /usr/sbin/nologin green
sudo groupadd -g 1003 blue  && sudo useradd -m -u 1003 -g 1003 -s /usr/sbin/nologin blue
sudo groupadd -g 1004 black && sudo useradd -m -u 1004 -g 1004 -s /usr/sbin/nologin black
sudo groupadd -g 1005 white && sudo useradd -m -u 1005 -g 1005 -s /usr/sbin/nologin white
```

Перевірка: `id red green blue black white` на VM2 має дати **ті самі числа**, що й на VM1.

## Крок 4. Каталоги, власники, права

```bash
sudo mkdir -p /nfs/public /nfs/private /nfs/incoming
```

### 4.1. `/nfs/public` — тільки читання

Каталог належить root і доступний усім для читання:

```bash
sudo chown root:root /nfs/public
sudo chmod 755 /nfs/public
echo "Публічний файл NFS" | sudo tee /nfs/public/readme.txt
sudo chmod 644 /nfs/public/readme.txt
```

Заборона запису тут ще й подвійна: і опцією `ro` в експорті, і правами (писати може лише root, а root клієнта все одно відображається на `nobody`).

### 4.2. `/nfs/private` — належить `red`

Усі запити з клієнта відобразяться на `red`, тож `red` має бути власником із повними правами:

```bash
sudo chown red:red /nfs/private
sudo chmod 700 /nfs/private
```

`700` означає, що все (читання, запис, вхід у каталог) дозволено лише власнику (`red`); а оскільки всі користувачі клієнта «стають» `red`, то всі вони мають доступ.

### 4.3. `/nfs/incoming` — права за варіантом (ACL)

Власник каталогу `green` (на нього відображається root клієнта), далі додаємо **іменні права** для інших трьох:

```bash
sudo chown green:green /nfs/incoming
sudo chmod 700 /nfs/incoming

sudo setfacl -m u:blue:rwx,u:white:r-x,u:black:--- /nfs/incoming
```

Перевір:

```bash
getfacl /nfs/incoming
```

Очікувано:

```
# file: nfs/incoming
# owner: green
# group: green
user::rwx
user:blue:rwx
user:black:---
user:white:r-x
group::---
mask::rwx
other::---
```

| Рядок | Значення |
|---|---|
| `user::rwx` | власник `green` — повні права (RWX) |
| `user:blue:rwx` | `blue` — читання, запис, вхід (RWX) |
| `user:white:r-x` | `white` — читати й заходити, але **не** створювати/видаляти (RX) |
| `user:black:---` | `black` — **нічого** |
| `other::---` | усі інші користувачі — нічого |
| `mask::rwx` | «стеля» прав для іменних записів (її обчислює система сама) |

Що означають прапорці `setfacl`:

| Частина | Значення |
|---|---|
| `-m` | modify: додати або змінити записи ACL |
| `u:blue:rwx` | запис «користувач `blue` має права `rwx`» |
| `r-x` | читання і вхід, без запису (`-` на місці `w`) |
| `---` | жодних прав |

> **Опційно.** Файли, які створить `blue`, належатимуть `blue`, а `green` за замовчуванням їх не змінить. Щоб власник каталогу завжди мав доступ до всього новоствореного, можна додати «ACL за замовчуванням»: `sudo setfacl -d -m u:green:rwx /nfs/incoming`. Для вимог завдання це не обов'язково.

## Крок 5. Експорти (`/etc/exports`)

```bash
sudo cp /etc/exports /etc/exports.orig
sudo nano /etc/exports
```

Вміст (підстав свої UID/GID з Кроку 1; тут red = 1001, green = 1002):

```
# /nfs/public: тільки читання, для мережі лабораторії
/nfs/public    192.168.106.0/24(ro,sync,no_subtree_check)

# /nfs/private: читання/запис, ТІЛЬКИ для вузла клієнта (VM2),
# усі користувачі клієнта відображаються на red
/nfs/private   192.168.106.20(rw,sync,all_squash,anonuid=1001,anongid=1001,no_subtree_check)

# /nfs/incoming: читання/запис для всієї мережі клієнта,
# root клієнта -> green, інші користувачі без змін
/nfs/incoming  192.168.106.0/24(rw,sync,root_squash,anonuid=1002,anongid=1002,no_subtree_check)
```

Розбір кожного рядка:

**`/nfs/public    192.168.106.0/24(ro,sync,no_subtree_check)`**

| Частина | Значення |
|---|---|
| `/nfs/public` | який каталог віддаємо |
| `192.168.106.0/24` | кому: усій лабораторній мережі (в завданні для public обмежень не задано) |
| `ro` | **тільки читання**, вимога завдання |
| `sync` | відповідати лише після фактичного запису на диск |
| `no_subtree_check` | вимкнути перевірку піддерева (рекомендовано) |

**`/nfs/private   192.168.106.20(rw,sync,all_squash,anonuid=1001,anongid=1001,no_subtree_check)`**

| Частина | Значення |
|---|---|
| `192.168.106.20` | **лише вузол клієнта** (VM2), а не вся мережа. Саме це вимагає завдання |
| `rw` | читання і запис |
| `all_squash` | **усіх** користувачів клієнта (включно з root) відображати на «анонімного» |
| `anonuid=1001,anongid=1001` | анонімом буде **`red`** (UID/GID 1001), а не `nobody` |

**`/nfs/incoming  192.168.106.0/24(rw,sync,root_squash,anonuid=1002,anongid=1002,no_subtree_check)`**

| Частина | Значення |
|---|---|
| `192.168.106.0/24` | **уся мережа**, де знаходиться клієнт |
| `rw` | читання і запис |
| `root_squash` | **root** клієнта відображається на анонімного (воно й так за замовчуванням, але пишемо явно для наочності) |
| `anonuid=1002,anongid=1002` | цим анонімом буде **`green`** |
| (немає `all_squash`) | **решта користувачів лишаються без змін**: `blue` на клієнті = `blue` (UID 1003) на сервері |

Застосувати й перевірити:

```bash
sudo exportfs -ra
sudo exportfs -v
sudo showmount -e localhost
```

| Команда | Що робить |
|---|---|
| `exportfs -r` | **повторно** синхронізувати ядро з `/etc/exports` |
| `exportfs -a` | застосувати **всі** експорти |
| `exportfs -v` | показати активні експорти **з усіма опціями** (включно з тими, що стоять за замовчуванням: `wdelay`, `root_squash`, `sec=sys` тощо) |
| `showmount -e localhost` | як виглядає список експортів для клієнта |

Очікуваний вивід `showmount -e`:

```
Export list for localhost:
/nfs/incoming 192.168.106.0/24
/nfs/private  192.168.106.20
/nfs/public   192.168.106.0/24
```

> Кожну зміну `/etc/exports` треба застосовувати командою `sudo exportfs -ra`, інакше сервер працює зі старими правилами.

## Крок 6. Фіксований порт `mountd` і запуск

За замовчуванням `mountd` слухає **випадковий** порт, який щоразу інший. Для аналізу трафіку і файрволів зручніше його зафіксувати.

```bash
sudo nano /etc/nfs.conf
```

Знайти секцію `[mountd]` (у ній рядки закоментовані) і розкоментувати/додати:

```ini
[mountd]
port=20048
```

Перезапуск:

```bash
sudo systemctl restart nfs-server
sudo systemctl enable nfs-server rpcbind
sudo rpcinfo -p localhost
```

`rpcinfo -p` показує таблицю `rpcbind`: які RPC-програми зареєстровані і на яких портах. Має бути приблизно:

```
   program vers proto   port  service
    100000    4   tcp    111  portmapper
    100000    3   tcp    111  portmapper
    100005    3   tcp  20048  mountd
    100005    3   udp  20048  mountd
    100003    3   tcp   2049  nfs
    100003    4   tcp   2049  nfs
    100021    4   tcp  ...    nlockmgr
```

Ось і всі компоненти з контрольного питання 3.3: `portmapper` (111), `mountd` (20048), `nfs` = `nfsd` (2049). Список слід додати до звіту.

> Якщо на VM1 увімкнений файрвол (`ufw`/`nftables`), відкрий TCP/UDP **111, 2049, 20048**. У стандартній Debian його немає.

### 7.2. Точки монтування

```bash
sudo mkdir -p /mnt/nfs/public /mnt/nfs/private /mnt/nfs/incoming
```

### 7.3. Монтування (NFSv3)

```bash

sudo mount -t nfs -o vers=3,proto=tcp nfs.color.edu:/nfs/private  /mnt/nfs/private
```

| Частина | Значення |
|---|---|
| `mount` | змонтувати файлову систему |
| `-t nfs` | тип файлової системи: NFS |
| `-o vers=3` | використати **NFSv3** (тоді працює повний ланцюжок `rpcbind` → `mountd` → `nfsd`) |
| `proto=tcp` | транспорт TCP (простіше для аналізу, ніж UDP) |
| `nfs.color.edu:/nfs/public` | **сервер:каталог на сервері** |
| `/mnt/nfs/public` | **локальна точка монтування** на клієнті |

Перевірка:

```bash

df -h | grep nfs
nfsstat -m
```

| Команда | Що показує |
|---|---|
| `mount \| grep nfs` | які NFS змонтовано і з якими опціями |
| `df -h` | розмір і заповненість віддалених ФС |
| `nfsstat -m` | для кожного монтування: сервер, версія, `rsize/wsize`, протокол |

> **Постійне монтування (необов'язково).** Для автоматичного монтування при старті додай у `/etc/fstab` на VM2 рядок:
> `nfs.color.edu:/nfs/public  /mnt/nfs/public  nfs  vers=3,ro,_netdev  0  0`.
> Опція `_netdev` каже системі чекати на мережу перед монтуванням.

## Крок 8. Перевірка поведінки

Усі команди на **VM2**. `sudo` дає виконання від **root** клієнта, а `sudo -u імʼя` від конкретного користувача. Це працює і для акаунтів із `nologin`, бо запускається команда, а не оболонка.

### 8.1. `/nfs/public` (тільки читання)

```bash
ls -l /mnt/nfs/public
cat /mnt/nfs/public/readme.txt
sudo touch /mnt/nfs/public/test.txt
```

Очікується: перегляд і читання працюють, а створення файлу дає

```
touch: cannot touch '/mnt/nfs/public/test.txt': Read-only file system
```

### 8.2. `/nfs/private` (усі → `red`)

```bash
sudo touch /mnt/nfs/private/from_root.txt          # root клієнта
sudo -u blue  touch /mnt/nfs/private/from_blue.txt  # blue клієнта
sudo -u black touch /mnt/nfs/private/from_black.txt # black клієнта
ls -ln /mnt/nfs/private
```

(`-n` у `ls` виводить **числа** UID/GID, а не імена.) Очікується, що **усі три** файли мають власника `1001` (тобто `red`):

```
-rw-r--r-- 1 1001 1001 0 ... from_black.txt
-rw-r--r-- 1 1001 1001 0 ... from_blue.txt
-rw-r--r-- 1 1001 1001 0 ... from_root.txt
```

Перевір на **сервері**:

```bash
ls -l /nfs/private
```

Усі файли належать `red:red`. Хто б не створював файл на клієнті, на сервері це `red`. Це і є `all_squash,anonuid=red`.

**Перевірка обмеження «лише для вузла клієнта»:** з іншої машини (наприклад, з VM1 або з хоста, `192.168.106.1`) спроба змонтувати `/nfs/private` має завершитися відмовою:

```bash
# на VM1 (це інша адреса, не 192.168.106.20)
sudo mkdir -p /mnt/test && sudo mount -t nfs -o vers=3 nfs.color.edu:/nfs/private /mnt/test
```

```
mount.nfs: access denied by server while mounting nfs.color.edu:/nfs/private
```

Для звіту ця відмова така ж важлива, як успішне монтування: вона показує, що `mountd` дійсно звіряє IP клієнта з `/etc/exports`.

### 8.3. `/nfs/incoming` (root → `green`, інші без змін, права за варіантом)

| Хто на клієнті | Дія | Очікування |
|---|---|---|
| **root** | створити файл | успіх, власник на сервері **`green`** (root → green) |
| **blue** | створити файл | успіх (RWX), власник на сервері **`blue`** (без змін) |
| **white** | переглянути список | успіх (RX) |
| **white** | створити файл | **Permission denied** (немає W) |
| **black** | переглянути список | **Permission denied** (немає нічого) |

Команди:

```bash
sudo touch /mnt/nfs/incoming/from_root.txt
sudo -u blue touch /mnt/nfs/incoming/from_blue.txt
sudo -u white ls /mnt/nfs/incoming
sudo -u white touch /mnt/nfs/incoming/from_white.txt
sudo -u black ls /mnt/nfs/incoming
ls -ln /mnt/nfs/incoming
```

Очікується:

```
-rw-r--r-- 1 1003 1003 0 ... from_blue.txt     <- blue лишився blue (UID 1003)
-rw-r--r-- 1 1002 1002 0 ... from_root.txt     <- root став green (UID 1002)

touch: cannot touch '/mnt/nfs/incoming/from_white.txt': Permission denied
ls: cannot open directory '/mnt/nfs/incoming': Permission denied     <- black
```

Перевір на **сервері**:

```bash
ls -l /nfs/incoming
```

```
-rw-r--r-- 1 blue  blue  0 ... from_blue.txt
-rw-r--r-- 1 green green 0 ... from_root.txt
```

Саме така картина підтверджує всю вимогу: root → `green`, `blue` залишився `blue`, а права вирішує ACL.

### 9.2. Запуск перехоплення (на VM1)

| Частина | Значення |
|---|---|
| `-i any` | слухати всі інтерфейси |
| `-n` | не перетворювати адреси на імена |
| `-vv` | **розшифровувати RPC/NFS**: `tcpdump` вміє декодувати заголовки RPC і показує тип операції |
| `host 192.168.106.20` | тільки трафік клієнта |
| `port 111` | `rpcbind` |
| `port 20048` | `mountd` (бо ми його зафіксували) |
| `port 2049` | `nfsd` |

Щоб зберегти трафік для Wireshark і додати до звіту:


У Wireshark зручні фільтри: `portmap`, `mount`, `nfs`, `rpc`.

### 9.3. Монтування, яке аналізуємо (на VM2)

```bash
sudo mount -t nfs -o vers=3,proto=tcp nfs.color.edu:/nfs/public /mnt/nfs/public
```

### 9.4. Що має бути видно (у порядку появи)

| № | Куди | Що | Зміст |
|---|---|---|---|
| 1 | клієнт → `:111` | **`PMAP GETPORT`** | «на якому порту програма 100005 (`mountd`) версії 3?» |
| 2 | `:111` → клієнт | відповідь | `20048` |
| 3 | клієнт → `:20048` | **`MOUNT NULL`**, потім **`MNT`** | запит на монтування шляху `/nfs/public` |
| 4 | `:20048` → клієнт | відповідь `MNT` | статус `OK` + **file handle** + дозволені методи автентифікації (`AUTH_SYS`) |
| 5 | клієнт → `:111` | `PMAP GETPORT` (nfs, v3) | «на якому порту `nfsd`?» → `2049` |
| 6 | клієнт → `:2049` | **`NFS NULL`, `FSINFO`, `GETATTR`, `PATHCONF`** | з'ясування можливостей і атрибутів кореня за отриманим file handle |

Це точно та сама послідовність, що в п. 1.6 теорії. Для порівняння: якщо спробувати змонтувати `/nfs/private` з не-клієнтського вузла (8.2), у кроці 4 замість `OK` прийде відмова (`MNT3ERR_ACCES`).

### 9.5. Передача файлів

Поки `tcpdump` працює, на VM2:

```bash
ls /mnt/nfs/public                       # READDIRPLUS / LOOKUP / ACCESS
cat /mnt/nfs/public/readme.txt           # LOOKUP, ACCESS, READ
sudo touch /mnt/nfs/public/x             # CREATE -> помилка NFS3ERR_ROFS
sudo touch /mnt/nfs/incoming/net_test    # LOOKUP, CREATE (успіх)
echo "дані" | sudo tee /mnt/nfs/incoming/net_test   # WRITE, COMMIT
```

| Дія на клієнті | Операція NFS у трафіку |
|---|---|
| `ls` | `ACCESS`, `READDIRPLUS` (список і атрибути файлів) |
| `cat файл` | `LOOKUP` (знайти ім'я), `READ` (прочитати дані) |
| `touch` у `incoming` | `LOOKUP`, `CREATE` |
| запис у файл | `WRITE`, `COMMIT` (зафіксувати на диску, через `sync`) |
| `touch` у `public` | `CREATE` → відповідь із помилкою **`NFS3ERR_ROFS`** (файлова система лише для читання) |
| `black` у `incoming` | відповідь **`NFS3ERR_ACCES`** (немає доступу) |

У кожному запиті на `:2049` видно **UID/GID** клієнта (в `AUTH_SYS`-частині RPC-заголовка): саме їх `nfsd` підставляє в перевірку прав, а потім squash змінює. У `tcpdump -vv` це видно як `uid ... gid ...`, а у Wireshark в полі `Credentials`.

### 9.6. Статистика й стан: `nfsstat`, `showmount`, `rpcinfo`

На **сервері (VM1)**:

```bash
nfsstat -s            # статистика сервера: скільки RPC-викликів, розбивка по операціях
showmount -a          # хто (з якого IP) що змонтував
showmount -d          # лише змонтовані каталоги
rpcinfo -p            # які RPC-програми зареєстровані
```

На **клієнті (VM2)**:

```bash
nfsstat -c            # статистика клієнта
nfsstat -m            # параметри кожного монтування
rpcinfo -p nfs.color.edu    # RPC-програми сервера (запит через мережу)
```

| Команда | Що показує |
|---|---|
| `nfsstat -s` | серверні лічильники: `Server rpc stats` (всього викликів, помилок автентифікації) і `Server nfs v3` (скільки `getattr`, `lookup`, `read`, `write`, `create`...) |
| `nfsstat -c` | те саме з боку клієнта |
| `nfsstat -m` | активні монтування: версія (`vers=3`), `proto`, розмір блоку (`rsize/wsize`), `hard`/`soft` тощо |
| `showmount -a` | «хто змонтував»: рядки `192.168.106.20:/nfs/public` |
| `showmount -e` | що експортується (з боку клієнта) |
| `rpcinfo -p` | зареєстровані RPC-програми і порти |

Порівняй `nfsstat -s` **до** і **після** серії команд із 9.5: лічильники `read`, `write`, `create`, `lookup` зростуть. Це простий доказ, що обмін справді йшов через NFS.

## Крок 10. (Додатково) NFSv4

NFSv4 не використовує `rpcbind`/`mountd`: усе йде через **TCP 2049**. Корисно показати різницю для контрольних питань.

```bash
sudo umount /mnt/nfs/public
sudo mount -t nfs -o vers=4.2 nfs.color.edu:/nfs/public /mnt/nfs/public
nfsstat -m
```

| Частина | Значення |
|---|---|
| `vers=4.2` | протокол NFSv4.2 |
| шлях `/nfs/public` | у Linux псевдо-корінь `v4` будується автоматично, тому той самий шлях працює |

У `tcpdump` (`port 2049`) видно лише **один порт** і жодного звернення до `:111` та `:20048`. Замість окремого `MNT` йдуть операції `PUTROOTFH`, `LOOKUP`, `GETFH`, `GETATTR` усередині протоколу NFS.

> Якщо в NFSv4 власники файлів виглядають як `nobody`, це проблема зіставлення імен (`idmapd`). Переконайся, що в `/etc/idmapd.conf` на обох машинах однаковий `Domain = color.edu`, або просто дивись числа через `ls -ln`.

Повернутися до v3: `sudo umount ...` і змонтувати з `vers=3`.

| Симптом | Причина / що робити |

# ЧАСТИНА 3. ВІДПОВІДІ НА КОНТРОЛЬНІ ЗАПИТАННЯ

**3.1. Відповідність NFS моделі ISO OSI.**
NFS є набором протоколів, що охоплюють кілька верхніх рівнів. Самі файлові операції та процедура монтування (протоколи NFS і MOUNT) відповідають **прикладному** рівню (7). Кодування даних у єдиному форматі (XDR) відповідає рівню **представлення** (6). Віддалений виклик процедур (ONC RPC) виконує функції **сеансового** рівня (5). Нижче працюють **транспортний** (TCP або UDP; у NFSv4 тільки TCP, порт 2049) і мережний (IP) рівні.

**3.2. Архітектура NFS.**
NFS побудована за моделлю «клієнт-сервер» поверх RPC. На сервері є список експортів (`/etc/exports`), служба `rpcbind` (довідник «програма → порт»), `mountd` (обробка запитів на монтування) і `nfsd` (виконання файлових операцій, потоки в ядрі), а для блокувань ще `statd` і `lockd`. Клієнт має NFS-клієнт у ядрі, який вбудований у віртуальну файлову систему (VFS), тому програми працюють з віддаленими файлами як із локальними. Запити передаються через RPC із кодуванням XDR. У NFSv2 і v3 сервер не зберігає стану (кожен запит самодостатній, об'єкти адресуються файловими дескрипторами), а NFSv4 є протоколом зі станом, де всі функції (включно з монтуванням і блокуваннями) об'єднано в один протокол на порту 2049.

**3.3. Призначення та функції компонент NFS: mountd, nfsd, rpcbind (portmapper).**
**`rpcbind` (portmapper, порт 111)** зберігає відповідність між номерами RPC-програм і портами, на яких вони слухають; клієнт спочатку питає в нього, де знаходиться потрібна служба. **`mountd`** обробляє запити на монтування: перевіряє `/etc/exports` і IP клієнта та, якщо доступ дозволено, повертає файловий дескриптор кореня експортованого каталогу; також веде список змонтованих клієнтів. **`nfsd`** (порт 2049) виконує власне файлові операції (читання, запис, створення, видалення тощо) за файловими дескрипторами, перевіряючи права за UID/GID із запиту; реалізований як набір потоків ядра.

**3.4. Процедура монтування файлової системи.**
У NFSv3: (1) клієнт звертається до `rpcbind` на сервері й дізнається порт `mountd`; (2) надсилає `mountd` запит `MNT` із шляхом експортованого каталогу; (3) `mountd` звіряє шлях та IP клієнта з `/etc/exports` і у разі дозволу повертає файловий дескриптор кореня й підтримувані методи автентифікації (інакше помилка доступу); (4) клієнт через `rpcbind` дізнається порт `nfsd` (2049) і виконує перші операції (`FSINFO`, `GETATTR`) за отриманим дескриптором; (5) ядро клієнта підключає віддалену файлову систему до локальної точки монтування, після чого всі звернення до неї перетворюються на NFS-операції (`LOOKUP`, `READ`, `WRITE`...). У NFSv4 процедура спрощена: клієнт одразу підключається до порту 2049 і отримує кореневий дескриптор операціями самого протоколу (`PUTROOTFH`, `LOOKUP`, `GETFH`), без `rpcbind` і `mountd`.
