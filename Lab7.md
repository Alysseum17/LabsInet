# ЧАСТИНА 1. ТЕОРІЯ — ПОЯСНЕННЯ ДЛЯ РОЗУМІННЯ Й ЗАХИСТУ

## 1.1. Що таке Web-сервіс і навіщо потрібен HTTP

**Web-сервіс** у контексті цієї лабораторної — сервер, який отримує **HTTP-запити** від клієнтів і надсилає **HTTP-відповіді** (сторінки HTML, текст, файли, JSON тощо). Зазвичай процес виглядає так:

1. Ти вводиш URL (наприклад, `https://www.color.edu:8449/`).
2. Клієнт визначає IP сервера за DNS (`www.color.edu` → `192.168.106.10`).
3. Клієнт встановлює TCP-з'єднання з потрібним портом (`8449`).
4. Для HTTPS додатково виконується **TLS-узгодження** і перевірка сертифіката.
5. Клієнт надсилає HTTP-запит, наприклад `GET / HTTP/1.1`.
6. Сервер перевіряє користувача й повертає HTTP-відповідь (`200 OK` або `401 Unauthorized`).

**HTTP (Hypertext Transfer Protocol)** — **прикладний протокол** у моделі TCP/IP. Він визначає, **який ресурс запитують**, **якою дією** (методом), **які метадані передають** (заголовки) та **що відповідає сервер**. HTTP не вимагає, щоб тіло відповіді було лише HTML: це може бути будь-який тип вмісту.

### Не плутати різні компоненти

| Компонент | Роль у запиті |
|---|---|
| DNS | Знаходить IP за ім'ям `www.color.edu` |
| IP | Доставляє пакети до вузла `192.168.106.10` |
| TCP | Установлює з'єднання та забезпечує впорядкований потік байтів |
| TLS | Шифрує та автентифікує захищене з'єднання (для HTTPS) |
| HTTP | Визначає запит `GET /`, заголовки й відповідь сервера |
| nginx | Програма, що реалізує HTTP/HTTPS на сервері |
| HTML | Один із форматів **тіла** HTTP-відповіді, не мережний протокол |

## 1.2. HTTP і HTTPS: у чому різниця

Зовні запит до одного й того ж сайту може бути однаковим, але **канал передачі різний**:

```text
HTTP:
клієнт ─ TCP ─ HTTP у відкритому вигляді ─────────────> nginx

HTTPS:
клієнт ─ TCP ─ TLS-захищений канал ─ HTTP усередині ─> nginx
```

| Ознака | HTTP | HTTPS |
|---|---|---|
| Шифрування | Немає | Є, через TLS |
| Звичайний порт | 80 | 443 |
| У нашій лабораторній | **8086** | **8449** |
| HTTP-методи | GET, HEAD, POST тощо | **Ті самі** методи |
| Передача Basic-пароля | Base64 можна прочитати у дампі | Той самий Basic усередині **шифрованого** TLS |
| Перевірка імені сервера | Ні через TLS | Сертифікат має бути виданий для `www.color.edu` |
| Що видно в `tcpdump` | Заголовки й тіло HTTP, якщо передача незашифрована | Рукостискання TLS і зашифровані дані, але не звичайний HTTP-текст |

> HTTPS — **не окремий набір HTTP-команд**. Це передача HTTP через захищений транспорт. HTTP Basic Auth сам по собі **не шифрує** пароль. Base64 ≠ encryption, тому Basic Auth на HTTP допускаємо тут **лише заради експерименту в ізольованій лабораторній мережі**, з окремими навчальними паролями. Для реальних систем автентифікацію потрібно передавати тільки через HTTPS.

## 1.3. URL, URI, домен, порт і шлях (контрольне питання 3.2)

Розберемо наш URL:

```text
https://www.color.edu:8449/docs/index.html?lang=uk#section2
  └──┘  └───────────┘ └──┘ └───────────────┘ └─────┘ └─────┘
 схема      host       port       path       query   fragment
```

| Частина | Приклад | Значення |
|---|---|---|
| **scheme** | `https` | Який протокол/схему використовувати |
| **host** | `www.color.edu` | Ім'я вузла, яке резолвиться DNS |
| **port** | `8449` | На який TCP-порт звертатись |
| **path** | `/docs/index.html` | Який ресурс потрібен на сервері |
| **query** | `lang=uk` | Параметри запиту, передаються серверу |
| **fragment** | `section2` | Посилання на частину документа; **не надсилається** серверу в HTTP-запиті |

**URI (Uniform Resource Identifier)** — ширше поняття: ідентифікатор ресурсу. **URL (Uniform Resource Locator)** — URI, який указує спосіб/місце доступу до ресурсу; наш `https://...` є і URI, і URL.

**URI ≠ файл на диску.** Шлях `/users/5` може обробляти програма і взагалі не мати однойменного файлу. Але в **нашому навчальному nginx зі статичною сторінкою** запит `/` за `root` і `index` приведе до `/var/www/color.edu/index.html`.

Якщо порт у URL відсутній, для `http://` браузер використовує типово **80**, а для `https://` — **443**. Тому без `:8086` або `:8449` до нашого nginx на потрібному порту не потрапиш.

## 1.4. Як виглядає HTTP-запит (контрольне питання 3.3)

HTTP/1.1 — текстова структура повідомлення. Приклад:

```http
GET / HTTP/1.1
Host: www.color.edu:8086
User-Agent: curl/8.x
Accept: */*

```

Останній **порожній рядок** означає завершення заголовків. Після нього, якщо є, починається **тіло** запиту.

**Структура:**

```text
[стартовий рядок]  GET / HTTP/1.1
[заголовок 1]      Host: www.color.edu:8086
[заголовок 2]      Accept: */*
[заголовок N]      ...
[порожній рядок]   \r\n
[тіло]             (для GET зазвичай відсутнє)
```

- **GET** — метод (що хочемо зробити).
- **/** — request target, шлях до ресурсу.
- **HTTP/1.1** — версія протоколу для цього повідомлення.
- **Host** — ім'я віртуального вебсервера; необхідний у звичайному HTTP/1.1-запиті. nginx вибирає `server_name` за цим ім'ям (разом з адресою/портом).
- **User-Agent** — програма-клієнт.
- **Accept** — бажані формати відповіді.
- **Authorization** — дані автентифікації; з'явиться в наступному запиті з Basic Auth.

Приклад із автентифікацією:

```http
GET / HTTP/1.1
Host: www.color.edu:8086
Authorization: Basic <base64(username:password)>

```

Замість `<base64(...)>` реально стоїть закодований рядок. Це **не хеш** і **не шифр**. Його можна декодувати, отримавши `username:password`.

### Важливо про Content-Length і Transfer-Encoding

Якщо передається тіло, сервер і клієнт мають розуміти його межі. Для HTTP/1.1 типові механізми: `Content-Length: N` (довжина у байтах) або **chunked transfer encoding** (`Transfer-Encoding: chunked`). У HTTP/2 і HTTP/3 формат кадрів інший, і такий самий текстовий стартовий рядок **на дроті не передається**.

## 1.5. HTTP-відповідь і статус-коди

```http
HTTP/1.1 200 OK
Server: nginx
Content-Type: text/html; charset=utf-8
Content-Length: 1234

<!doctype html> ...
```

**Структура:** рядок статусу → заголовки → порожній рядок → тіло.

| Код | Назва | Що означає / коли побачимо |
|---|---|---|
| **200** | OK | Користувач успішно увійшов і отримав сторінку |
| **201** | Created | Створено ресурс (приклад для API, не вимога нашої статичної сторінки) |
| **301/302** | Moved Permanently / Found | Перенаправлення за новою адресою |
| **304** | Not Modified | Ресурс не змінився, тіло повторно не надсилається |
| **400** | Bad Request | Некоректний синтаксис запиту |
| **401** | Unauthorized | **Немає дійсних облікових даних**; сервер зазвичай відповідає з `WWW-Authenticate` |
| **403** | Forbidden | Сервер зрозумів запит, але доступ заборонив |
| **404** | Not Found | Ресурс не знайдено |
| **405** | Method Not Allowed | Метод не дозволений для ресурсу (наприклад, POST для статичної сторінки) |
| **500** | Internal Server Error | Помилка на сервері |
| **502** | Bad Gateway | Проксі не отримав коректну відповідь від upstream |
| **503** | Service Unavailable | Сервіс тимчасово не готовий |

Класи кодів: `1xx` — інформаційні, `2xx` — успіх, `3xx` — перенаправлення, `4xx` — помилка з боку клієнтського запиту/доступу, `5xx` — серверна помилка.

### Що саме відбувається під час Basic Auth

```text
VM2 / curl                              VM1 / nginx
    |                                        |
    | GET / (без Authorization)              |
    |--------------------------------------->|
    | 401 Unauthorized                       |
    | WWW-Authenticate: Basic realm="Lab7"   |
    |<---------------------------------------|
    | GET /                                  |
    | Authorization: Basic ...               |
    |--------------------------------------->|
    | 200 OK + HTML (за правильного пароля)  |
    |<---------------------------------------|
```

**`401` тут — очікувана правильна поведінка**, а не поломка сервера. Щоб продемонструвати `401`, використовуй `curl` без `-u`. Деякі клієнти з `-u red` надсилають Basic-дані **одразу**, тому окремої першої відповіді `401` у цьому випадку може не бути.

## 1.6. HTTP-методи (контрольне питання 3.4)

| Метод | Призначення | Safe? | Idempotent? |
|---|---|---|---|
| **GET** | Прочитати представлення ресурсу | Так | Так |
| **HEAD** | Те саме, що GET, але **без тіла** відповіді | Так | Так |
| **POST** | Передати дані серверу для обробки | Ні | Зазвичай ні |
| **PUT** | Створити/замінити представлення за вказаним URI | Ні | Так |
| **PATCH** | Частково змінити ресурс | Ні | Не гарантовано |
| **DELETE** | Видалити ресурс | Ні | Так |
| **OPTIONS** | Дізнатися комунікаційні можливості сервера/ресурсу | Так | Так |
| **TRACE** | Діагностичне віддзеркалення запиту | Так за семантикою | Так; часто вимкнений із міркувань безпеки |
| **CONNECT** | Створити тунель через проксі | Ні | Ні |

**Safe** означає, що клієнт **не просить** змінювати стан сервера (навіть якщо сервер побічно пише журнал). **Idempotent** означає, що багаторазове повторення **має той самий задуманий ефект**, що й один запит.

- `GET /users` — безпечно читати кілька разів.
- `PUT /users/5` з однаковим вмістом — повтори залишають той самий результат.
- `POST /orders` — два запити можуть створити **два замовлення**.
- `DELETE /users/5` — повторний запит може повернути вже інший статус, але бажаний кінцевий стан (ресурс видалений) той самий.

**Нюанс:** встановлений у цій роботі nginx **роздає статичні файли**; на ньому **не виникає API автоматично**. `POST /` може закономірно дати `405` — це **не суперечить** загальній теорії POST.

## 1.7. Stateless HTTP, сесії, cookies (контрольне питання 3.5)

**HTTP — stateless (без стану) на рівні семантики запитів:** кожен запит має достатньо інформації, щоб його обробити; HTTP сам по собі не гарантує збереження стану входу, корзини чи профілю між окремими запитами.

Але сайти створюють **стан на рівні застосунку** через:

1. **Cookies.** Сервер: `Set-Cookie: sessionid=...; HttpOnly; Secure; SameSite=Lax`, браузер у наступних запитах додає `Cookie: sessionid=...`.
2. **Серверне сховище сесій.** `sessionid` стає ключем до даних на сервері (хто увійшов, налаштування).
3. **Токени** (наприклад, Bearer), які клієнт додає до наступних запитів.
4. **HTTP Basic** — клієнт передає ім'я/пароль під час запитів до захищеного ресурсу.

```text
Запит 1: GET /login   ──> Set-Cookie: sessionid=abc123
Запит 2: GET /profile, Cookie: sessionid=abc123

Сервер: abc123 → дані відповідного користувача.
```

**Не плутати:**

- **HTTP-сесія програми** (cookie + session store) — логічний стан користувача.
- **TCP-з'єднання** — транспортний канал між процесами.
- **TLS-сесія** — криптографічні параметри захищеного зв'язку.
- **Basic Auth** — автентифікація через заголовок кожного відповідного запиту; **сесійного cookie ми тут не створюємо**.

Наш nginx демонструє **Basic Auth**, не «логін-форму із cookie».

## 1.8. Кешування HTTP (контрольне питання 3.6)

**Кеш** зберігає відповідь на запит, щоб не передавати незмінні дані повторно. Це скорочує затримку, навантаження й трафік.

| Заголовок | Сенс |
|---|---|
| `Cache-Control: max-age=60` | Відповідь може вважатися свіжою 60 секунд відповідно до інших правил кешування |
| `Cache-Control: public` | Відповідь може кешуватися і спільним кешем за відповідних умов |
| `Cache-Control: private` | Призначена для приватного кешу користувача, не для загального кешу |
| `Cache-Control: no-cache` | **Не означає «заборонено зберігати»**; перед повторним використанням потрібна перевірка на сервері |
| `Cache-Control: no-store` | Не зберігати запит/відповідь у кеші |
| `ETag: "abc"` | Ідентифікатор конкретної версії представлення |
| `If-None-Match: "abc"` | Клієнт питає, чи досі актуальна раніше відома версія |
| `Last-Modified` | Час останньої зміни ресурсу |
| `If-Modified-Since` | Умовний запит щодо часу зміни |

**Умовний GET:**

```text
1) GET /index.html
   ← 200 OK, ETag: "v1", тіло HTML

2) GET /index.html, If-None-Match: "v1"
   ← 304 Not Modified, тіло не передається
```

У лабораторній сторінка захищена Basic Auth, тому для практичного конфігу використаємо `Cache-Control: no-store` — так не накопичуватимемо приватний вміст у кеші. **Теоретично** conditional requests / ETag усе одно важливо знати. Додатковий ручний запит із `If-None-Match` можна зробити **лише як демонстрацію логіки HTTP**, а не як доказ реального кешування браузером у режимі `no-store`.

## 1.9. Постійні з'єднання (Keep-Alive; контрольне питання 3.7)

Без повторного використання з'єднання для кожного ресурсу довелося б робити новий TCP handshake (і TLS handshake для HTTPS).

```text
Без keep-alive:
TCP connect → GET /index.html → TCP close
TCP connect → GET /style.css  → TCP close

Із keep-alive:
TCP connect → GET /index.html → response
            → GET /style.css  → response → TCP close пізніше
```

Для **HTTP/1.1** з'єднання зазвичай за замовчуванням **постійне**, якщо немає `Connection: close` або іншої причини його завершити. Сервер має власний тайм-аут неактивності. У нашому nginx це можна налаштувати `keepalive_timeout 65s;` (секунди).

**HTTP/2** передає кілька потоків (streams) через одне з'єднання; на відміну від HTTP/1.1, запити можуть мультиплексуватися. **HTTP/3** використовує QUIC поверх UDP, а не TCP. Методичка переважно розглядає класичний HTTP/1.1; його й зафіксуємо для мережних експериментів через `curl --http1.1`.

## 1.10. Як nginx приймає й обробляє запит

nginx має **master process** (керує конфігурацією/worker-процесами) і **worker processes**, які обслуговують запити. У Debian основний конфіг зазвичай `/etc/nginx/nginx.conf`, а додаткові сайти — у `/etc/nginx/sites-available/` з посиланнями із `/etc/nginx/sites-enabled/`.

Наші головні директиви:

| Директива | Функція |
|---|---|
| `server { ... }` | Віртуальний вебсервер (конфігурація для певного порту/імені) |
| `listen 192.168.106.10:8086;` | Приймати HTTP на заданій IP-адресі й порту |
| `listen 192.168.106.10:8449 ssl;` | Приймати HTTPS із TLS |
| `server_name www.color.edu;` | Обслуговувати ім'я хоста |
| `root /var/www/color.edu;` | Каталог зі статичними файлами |
| `index index.html;` | Який файл віддавати для запиту `/` |
| `auth_basic "...";` | Увімкнути HTTP Basic Authentication, задає `realm` |
| `auth_basic_user_file ...;` | Де лежить файл із користувачами та **хешами** паролів |
| `ssl_certificate` | Публічний TLS-сертифікат вебсервера |
| `ssl_certificate_key` | Приватний ключ вебсервера (секрет) |
| `location /` | Правила обробки шляхів усередині сайту |
| `try_files $uri $uri/ =404;` | Шукати відповідний файл/каталог; якщо немає — 404 |

**Важливо:** для нашого випадку `auth_basic` буде на рівні **обох блоків `server`**, щоб випадково не залишити `/other.html` незахищеним через інший `location`.

## 1.11. HTTP Basic Authentication і файл `.htpasswd`

Наші три логіни не зобов'язані відповідати Unix-акаунтам і **не використовують** автоматично користувачів Samba/Postfix/Dovecot із попередніх лабораторних. Ми створимо **окремі веблогіни** `red`, `greenu`, `blue` та окремі навчальні паролі.

У файлі `.htpasswd` записи виглядають приблизно так:

```text
red:<хеш-пароля-red>
greenu:<хеш-пароля-greenu>
blue:<хеш-пароля-blue>
```

`htpasswd` зберігає **хеш**, а не відкритий пароль. Будемо використовувати `htpasswd -B` (bcrypt). Файл розміщуємо в **`/etc/nginx/`, поза `root` сайту**, а не в `/var/www/color.edu`, щоби його не можна було випадково завантажити через веб.

- Немає заголовка `Authorization` → `401`.
- Користувача немає у файлі → `401`.
- Користувач є, але пароль хибний → `401`.
- Правильний логін і пароль → `200`, якщо ресурс існує.
- Лише ім'я `green` замість `greenu` → `401`.

## 1.12. TLS, CA, CSR, SAN: повний ланцюжок довіри

Для HTTPS потрібно **два різних типи ключів/сертифікатів**:

```text
                    CA із ЛР3 (www-сертифікат не є CA)
         приватний ключ CA: ~/ca/private/ca.key.pem  [нікому не віддавати]
                              │
                              │ підписує CSR
                              ▼
        cert: www.color.edu  ←→  private key: www.color.edu.key.pem
                   │                         │
                   └──────── nginx ─────────┘
                              │
                VM2 довіряє публічному сертифікату CA
                й перевіряє ім'я www.color.edu у SAN
```

Терміни:

| Термін | Розшифрування / призначення |
|---|---|
| **Private key** | Закритий ключ сервера: ним доводять володіння сертифікатом у TLS; не публікувати |
| **Public key** | Відкритий ключ у сертифікаті; його можуть бачити клієнти |
| **CSR** | Certificate Signing Request — заявка на сертифікат із публічним ключем і Subject |
| **CA** | Certificate Authority — центр сертифікації, який підписує сертифікати |
| **Issuer** | Хто видав сертифікат (наш `color CA`) |
| **Subject** | Кому він виданий (`CN=www.color.edu` і службові поля) |
| **SAN** | Subject Alternative Name — імена, для яких сертифікат дійсний. **Потрібно `DNS:www.color.edu`** |
| **CA:FALSE** | Сертифікат належить вебсерверу, а не має права видавати інші сертифікати |
| **serverAuth** | Розширення EKU для автентифікації вебсервера |

**Чому недостатньо `CN=www.color.edu`?** Сучасні TLS-клієнти перевіряють ім'я насамперед за **SAN**. Тому в цій лабораторній **явно додаємо `subjectAltName = DNS:www.color.edu` під час підписування**, навіть якщо у попередній ЛР3 сертифікати створювалися без SAN.

**Чому ми не робимо новий CA?** У п. 2.2 чітко сказано **підписати сертифікатом і ключем CA, створеного в ЛР3**. Новий самопідписаний сертифікат вебсервера тут **не виконає вимогу**.

## 1.13. Як відбувається TLS handshake

Спрощена схема для сучасного TLS 1.3:

```text
VM2                                               VM1/nginx
  │                                                  │
  │ TCP three-way handshake                          │
  │ SYN  → SYN/ACK → ACK                             │
  │                                                  │
  │ ClientHello (версії, cipher suites, SNI, key share)
  │ ─────────────────────────────────────────────────> │
  │ ServerHello (обрана версія/параметри)             │
  │ <───────────────────────────────────────────────── │
  │ Далі зашифровані: EncryptedExtensions, Certificate,
  │ CertificateVerify, Finished                       │
  │ <───────────────────────────────────────────────── │
  │ Finished                                         │
  │ ─────────────────────────────────────────────────> │
  │ TLS захищений ─── HTTP GET / усередині TLS ─────> │
  │ <── TLS-зашифрована HTTP-відповідь ─────────────── │
```

**Що перевіряє клієнт:** сертифікат підписано довіреним CA, він чинний за датами, ім'я сервера є в SAN, призначення сертифіката підходить для сервера. TLS також забезпечує перевірку цілісності й узгодження криптографічних параметрів.

Нюанс для Wireshark: у **TLS 1.2** серверний `Certificate` зазвичай іще видно відкрито; у **TLS 1.3** повідомлення сертифіката передається вже зашифрованим після `ServerHello`. Тому відсутність відкритого сертифіката у дампі **не означає**, що сервер його не надсилав.

## 1.14. DNS A-запис, `Host`, `server_name` і SNI — чотири різні речі

Ці поняття часто плутають:

| Рівень | Що передаємо | Для чого |
|---|---|---|
| DNS | `www.color.edu A 192.168.106.10` | Знайти IP сервера |
| TCP | `192.168.106.10:8449` | Куди встановити з'єднання |
| TLS / SNI | `www.color.edu` | Сервер може вибрати потрібний сертифікат під час handshake |
| HTTP/1.1 / Host | `Host: www.color.edu:8449` | Вибрати правильний віртуальний вебсайт у nginx |

`curl --resolve www.color.edu:8449:192.168.106.10 https://www.color.edu:8449/` — корисний діагностичний прийом: вручну вказує IP **тільки для цього curl-запиту**, але залишає URL-ім'я для HTTP Host, TLS SNI та перевірки сертифіката. Це **не замінює виконання обов'язкового пункту з DNS**, а лише допомагає відділити проблему DNS від проблеми nginx/TLS.

## 1.15. Версії HTTP і актуальні специфікації

Методичка посилається на RFC 1945, 6265, 7230, 7234, 7540 — ці документи допомагають розібрати історію HTTP. Сучасна база HTTP (додатковий контекст, **не зміна завдання**):

| Стандарт | Тема |
|---|---|
| **RFC 9110** | Семантика HTTP: ресурси, методи, статуси, заголовки |
| **RFC 9111** | HTTP caching |
| **RFC 9112** | HTTP/1.1: синтаксис, framing, управління з'єднаннями |
| **RFC 9113** | HTTP/2 |
| **RFC 9114** | HTTP/3 |
| **RFC 6265** | Cookies / стан на стороні клієнта |
| **RFC 7617** | HTTP Basic Authentication |

**План далі спеціально використовує HTTP/1.1**, щоб можна було читати стартовий рядок і заголовки звичайними `telnet` / `nc` та в Wireshark.

## Крок 2. Додати `www.color.edu` у DNS (пункт 2.6)

**Машина: VM1 (первинний DNS-сервер BIND9).** На VM2 **не редагуємо** зону — вона реплікується з VM1 через AXFR/IXFR, як у ЛР2.

### 2.1. Перед редагуванням — резервна копія

```bash

  /etc/bind/zones/db.color.edu.pre-lab7.bak

```

### 2.2. Додати лише **один потрібний A-запис**

```bash
sudo nano /etc/bind/zones/db.color.edu
```

У зону `color.edu` із ЛР2/ЛР3 **дописати** (за умови, що такого запису ще немає):

```dns
; ----- Вебсервер з лабораторної №7 -----
www     IN      A       192.168.106.10
```

Якщо в зоні `$ORIGIN color.edu.`, відносне ім'я `www` означає **`www.color.edu.`**. Запис `www IN A 192.168.106.10` правильніший за спробу `www.color.edu IN A ...` **без крапки**: друга форма може помилково перетворитися на `www.color.edu.color.edu.`.

**Також збільшити число `Serial` усередині наявного SOA-запису**. Наприклад, якщо було:

```dns
@ IN SOA ns1.color.edu. admin.color.edu. (
    2026093001 ; Serial
    3600       ; Refresh
    900        ; Retry
    604800     ; Expire
    86400 )    ; Negative TTL
```

можна змінити **лише Serial** на `2026102301`, **але тільки якщо він справді більший за теперішній**. У твоїй живій зоні число може бути іншим: подивися реальне значення й збільш його. Не копіюй приклад сліпо.

**Чому Serial треба збільшувати:** вторинний DNS-сервер порівнює серійний номер SOA і вирішує, чи потрібно забирати нову версію зони. Якщо записати `www`, але лишити старий Serial, VM2 може продовжувати віддавати старі дані.

> **Чого не стирати:** усі записи `ns1`, `ns2`, `mail`, `MX`, `red`, `green`, `blue`, `black`, `white`, `ws1`–`ws5` та інші записи з попередніх робіт. Нам потрібне лише **доповнення** зони.

sudo named-checkconf
sudo rndc reload color.edu

### 2.6. Перевірити **системне** розв'язування імен (важливо!)

```bash
# На VM2:

```

Ця команда має повернути `192.168.106.10`. Якщо `dig @192.168.106.10` працює, але `getent` — ні, значить **BIND відповідає правильно**, однак ОС клієнта може використовувати **чужий DNS-сервер** (наприклад DNS NAT-мережі).

Якщо VM2 працює з **systemd-resolved**, перевір:

```bash

```

Для тимчасового налаштування DNS саме для лабораторного домену (якщо `systemd-resolved` активний; заміни інтерфейс, якщо інший):

```bash
sudo resolvectl dns enp0s8 192.168.106.10 192.168.106.20
sudo resolvectl domain enp0s8 '~color.edu'
resolvectl query www.color.edu
```

`~color.edu` — **routing domain**: запити для цього домену спрямовуються через DNS, зазначені для інтерфейсу. Налаштування `resolvectl` такого типу можуть зникати після перезавантаження; для постійних змін використовуй **наявний мережний менеджер** VM, а не редагуй навмання згенерований `/etc/resolv.conf`.

Як діагностичний запасний варіант (тільки перевірка nginx, не заміна DNS-завдання):

```bash
curl --resolve www.color.edu:8086:192.168.106.10 \
  -I http://www.color.edu:8086/
```

Отримати `401` на цій команді — уже добра ознака: HTTP-сервер досяжний, але потребує автентифікації.

## Крок 4. Створити **точно трьох** вебкористувачів

**VM1**, окремі користувачі HTTP Basic Auth. Не потрібно змінювати Linux/Samba/поштові паролі зі старих лаб.

```bash
# Створити файл і запис першого користувача
sudo htpasswd -cB /etc/nginx/.htpasswd-color red

# Додати другого (без -c, щоб НЕ стерти red!)
sudo htpasswd -B /etc/nginx/.htpasswd-color greenu

# Додати третього
sudo htpasswd -B /etc/nginx/.htpasswd-color blue
```

**Під час кожної команди введи окремий навчальний пароль**, який не використовуєш у реальних акаунтах. Команда запитає пароль інтерактивно. **Не додавай `-b`** з паролем прямо в командний рядок: він потрапить в історію або список процесів.

**Навіщо опції:**

| Опція | Що робить |
|---|---|
| `-c` | Створює файл **з нуля**. Використовуй **тільки для першого користувача** |
| `-B` | Створює bcrypt-хеш пароля (для сучасного Debian) |
| без `-c` | Додає або оновлює один запис, зберігаючи решту |

Обмежити читання файлу:

```bash
sudo chown root:www-data /etc/nginx/.htpasswd-color
sudo chmod 640 /etc/nginx/.htpasswd-color

# Подивитися лише ІМЕНА, а не показувати хеші паролів:
sudo cut -d: -f1 /etc/nginx/.htpasswd-color
```

Очікувані імена:

```text
red
greenu
blue
```

**Чому `root:www-data` і `640`:** root може читати/змінювати, nginx-worker (зазвичай член групи `www-data`) — читати, решта користувачів — ні. `htpasswd` формує хеші паролів; файл усе одно потрібно захистити від сторонніх.

> У методичці не вказано конкретні паролі. Ти задаєш їх сам; для захисту пам'ятай або безпечно збережи **три навчальні паролі**. Не вставляй їх у звіт, скріншоти чи файл `Lab7.md`.

## Крок 5. Випустити сертифікат **`www.color.edu` через CA із ЛР3**

Це один із найважливіших етапів: **не самопідписаний вебсертифікат**, а CSR → підпис тим самим `color CA`.

У ЛР3 ми створювали **класичну структуру OpenSSL CA** у `~/ca`:

```text
~/ca/
├── openssl.cnf
├── certs/
│   ├── ca.cert.pem                 # сертифікат CA
│   ├── mail.color.edu.cert.pem     # попередній сертифікат
│   └── ...
├── private/
│   ├── ca.key.pem                  # приватний ключ CA
│   └── ...
├── newcerts/                      # журнал виданих сертифікатів
├── index.txt
└── serial
```

### 5.1. Перейти в **наявну** теку CA

```bash
cd ~/ca
pwd
ls -l openssl.cnf index.txt serial certs/ca.cert.pem private/ca.key.pem

# Який серійний номер буде у наступного сертифіката?
cat serial

# Хто видає сертифікати?
openssl x509 -in certs/ca.cert.pem -noout -subject -issuer
```

**Очікувано:** у Subject/Issuer CA побачиш `CN = color CA` з даними варіанту 6 (`C=UA`, `ST=Ukraine`, `L=Kyiv`, `O=KPI`, `OU=OT`). Не треба переписувати `serial` — `openssl ca` сам керує ним.

### 5.2. Створити **окремий** приватний ключ вебсервера

```bash
umask 077
openssl genpkey -algorithm RSA \
  -pkeyopt rsa_keygen_bits:2048 \
  -out private/www.color.edu.key.pem

chmod 600 private/www.color.edu.key.pem
```

**Пояснення:** ключ вебсервера — **не той самий**, що ключ CA. CA-підпис використовує `private/ca.key.pem`, а nginx працює зі своїм `www.color.edu.key.pem`. Це принцип розділення повноважень: компрометація одного вебсервера не повинна автоматично означати компрометацію кореневого CA.

### 5.3. Створити CSR на `www.color.edu`

```bash
openssl req -new \
  -key private/www.color.edu.key.pem \
  -subj "/C=UA/ST=Ukraine/L=Kyiv/O=KPI/OU=OT/CN=www.color.edu" \
  -out www.color.edu.csr.pem

openssl req -in www.color.edu.csr.pem -noout -subject -verify
```

Важливі фрагменти:

- `-new` — створити **Certificate Signing Request**, а не готовий сертифікат;
- `-key` — закритий ключ, публічна частина якого увійде в сертифікат;
- `-subj ... CN=www.color.edu` — ім'я нашого вебсервера;
- інші поля відповідають полям CA із ЛР3, щоб пройти `policy_match` у `openssl.cnf`;
- `-verify` — перевіряє підпис самого CSR (тобто що заявник володіє відповідним ключем).

### 5.4. Задати **SAN** для серверного сертифіката

Створюємо окремий файл розширень, щоб **гарантовано** було `DNS:www.color.edu`:

```bash
nano www.color.edu.ext.cnf
```

```ini
[ web_server ]
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature, keyEncipherment
extendedKeyUsage = serverAuth
subjectKeyIdentifier = hash
authorityKeyIdentifier = keyid,issuer
subjectAltName = DNS:www.color.edu
```

**Чому це важливо:** старий `openssl.cnf` із ЛР3 може мати лише `[server_cert]` без SAN. Наші розширення додають **правильне ім'я для сучасних TLS-клієнтів**. `CA:FALSE` і `serverAuth` теж гарантують правильну роль сертифіката.

### 5.5. Підписати через **`openssl ca`**, а не створити новий CA

Запускаємо з каталогу `~/ca`:

```bash
openssl ca \
  -config openssl.cnf \
  -extfile www.color.edu.ext.cnf \
  -extensions web_server \
  -days 365 -notext -md sha256 \
  -in www.color.edu.csr.pem \
  -out certs/www.color.edu.cert.pem
```

Якщо запитає:

```text
Sign the certificate? [y/n]:
1 out of 1 certificate requests certified, commit? [y/n]:
```

відповісти `y` двічі, **лише якщо Subject і розширення правильні**.

**Що змінилося:**

- `certs/www.color.edu.cert.pem` — новий готовий сертифікат;
- `newcerts/<serial>.pem` — його архівна копія;
- `index.txt` — запис про видачу;
- `serial` — автоматично збільшиться;
- **наявні сертифікати поштових серверів залишаться на місці**.

### 5.6. Перевірити сертифікат **до налаштування nginx**

```bash
# Хто підписав, для кого виданий, який строк дії?
openssl x509 -in certs/www.color.edu.cert.pem \
  -noout -subject -issuer -dates

# Розширення SAN і призначення:
openssl x509 -in certs/www.color.edu.cert.pem \
  -noout -ext subjectAltName,extendedKeyUsage,basicConstraints

# Перевірити підпис CA і саме ім'я www.color.edu:
openssl verify \
  -CAfile certs/ca.cert.pem \
  -verify_hostname www.color.edu \
  certs/www.color.edu.cert.pem
```

Правильний результат останньої команди:

```text
certs/www.color.edu.cert.pem: OK
```

Інші ознаки успіху:

```text
subject=... CN=www.color.edu
issuer=... CN=color CA
X509v3 Subject Alternative Name:
    DNS:www.color.edu
```

**Якщо `openssl verify` не дає OK** — не підключай такий сертифікат до nginx, доки не з'ясуєш причину (інший CA, відсутній SAN, неправильний Subject, часова помилка тощо).

### 5.7. Скопіювати лише **серверний** ключ і сертифікат для nginx

```bash
sudo install -d -m 700 /etc/nginx/tls

sudo install -o root -g root -m 600 \
  ~/ca/private/www.color.edu.key.pem \
  /etc/nginx/tls/www.color.edu.key.pem

sudo install -o root -g root -m 644 \
  ~/ca/certs/www.color.edu.cert.pem \
  /etc/nginx/tls/www.color.edu.cert.pem

sudo ls -l /etc/nginx/tls/
```

- `key.pem` з правами `600`: приватний ключ може читати лише root (master-процес nginx у Debian стартує від root, тому це нормально).
- `cert.pem` з правами `644`: це **публічний** сертифікат.
- **Не копіювати `ca.key.pem`** у теку nginx: серверу не потрібен приватний ключ CA!

## Крок 6. Налаштувати nginx на HTTP `8086` та HTTPS `8449`

### 6.1. Створити окремий конфіг сайту

На VM1:

```bash
sudo nano /etc/nginx/sites-available/color.edu
```

**Повний робочий приклад для 6-го варіанту:**

```nginx
# ---- HTTP: 8086 ----
server {
    listen 192.168.106.10:8086;
    server_name www.color.edu;

    root /var/www/color.edu;
    index index.html;

    # Обов'язкова автентифікація для ВСЬОГО сайту
    auth_basic "Lab7 - color.edu";
    auth_basic_user_file /etc/nginx/.htpasswd-color;

    # Не зберігати захищений контент у кеші
    add_header Cache-Control "no-store" always;

    access_log /var/log/nginx/color-http.access.log;
    error_log  /var/log/nginx/color-http.error.log warn;

    keepalive_timeout 65s;

    location / {
        try_files $uri $uri/ =404;
    }
}

# ---- HTTPS: 8449 ----
server {
    listen 192.168.106.10:8449 ssl;
    server_name www.color.edu;

    root /var/www/color.edu;
    index index.html;

    # Сертифікат, підписаний CA із лабораторної №3
    ssl_certificate     /etc/nginx/tls/www.color.edu.cert.pem;
    ssl_certificate_key /etc/nginx/tls/www.color.edu.key.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    # Та сама автентифікація і для HTTPS
    auth_basic "Lab7 - color.edu";
    auth_basic_user_file /etc/nginx/.htpasswd-color;

    add_header Cache-Control "no-store" always;

    access_log /var/log/nginx/color-https.access.log;
    error_log  /var/log/nginx/color-https.error.log warn;

    keepalive_timeout 65s;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

**Розбір основних рядків:**

| Фрагмент | Для чого |
|---|---|
| `listen 192.168.106.10:8086` | HTTP доступний лише на Host-only IP лабораторії, а не на всіх інтерфейсах VM |
| `listen 192.168.106.10:8449 ssl` | HTTPS на конкретному TCP-порту з увімкненим TLS |
| `server_name www.color.edu` | Ім'я сервера з таблиці варіанта 6 |
| `root` + `index` | Віддавати створену сторінку з `/var/www/color.edu/index.html` |
| `auth_basic` | Для доступу до **будь-якого** ресурсу сайту потрібна Basic Auth |
| `auth_basic_user_file` | Файл **із трьома вебкористувачами**, не `/etc/passwd` |
| `ssl_certificate` | Публічний сертифікат `www.color.edu`, підписаний CA |
| `ssl_certificate_key` | Приватний ключ **саме цього сервера**, не CA |
| `ssl_protocols` | Обмежити TLS до 1.2/1.3 |
| `add_header Cache-Control "no-store" always` | Для прикладу не кешувати приватний вміст; `always` додає заголовок і до кодів помилок |
| `access_log`, `error_log` | Окремі журнали для HTTP і HTTPS — зручно для аналізу |
| `keepalive_timeout` | Як довго сервер тримає неактивне постійне з'єднання |
| `try_files ... =404` | Якщо ресурсу немає — чесна відповідь 404 |

> Чому **не робимо HTTP → HTTPS редирект автоматично?** У цій лабораторній **обидва протоколи** потрібно дослідити окремо, зокрема HTTP-заголовки та Basic Auth у відкритому вигляді. Якщо одразу робити `301` на HTTPS, тест «звичайний HTTP + автентифікація» не матиме тієї самої поведінки. **Для реального публічного вебсайту** варто перенаправляти HTTP на HTTPS і не приймати паролі в HTTP.

### 6.2. Увімкнути свій сайт і вимкнути стандартний

```bash
# Посилання із sites-enabled на наш конфіг:
sudo ln -s /etc/nginx/sites-available/color.edu \
  /etc/nginx/sites-enabled/color.edu

# Лише стандартний nginx-сайт (не видаляє сам файл конфігу):
if [ -L /etc/nginx/sites-enabled/default ]; then
    sudo rm /etc/nginx/sites-enabled/default
fi
```

Якщо посилання `color.edu` **вже існує**, команда `ln -s` повідомить `File exists`; повторно створювати його не треба. Якщо на VM1 уже були **інші** сайти nginx, не вимикай їх без потреби — вимкнення `default` тут розраховано на чисте встановлення nginx після ЛР1–6.

### 6.3. Перевірити конфіг **до перезапуску**

```bash
sudo nginx -t
```

Очікується:

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

Якщо бачиш `emerg`, `permission denied`, `cannot load certificate` або `duplicate listen` — виправ помилку **до `reload`**.

### 6.4. Застосувати налаштування

```bash
sudo systemctl reload nginx
sudo systemctl status nginx --no-pager

sudo ss -lntp | grep -E ':(8086|8449)\b'
```

Очікувана сутність результату:

```text
LISTEN ... 192.168.106.10:8086 ... nginx
LISTEN ... 192.168.106.10:8449 ... nginx
```

**Якщо nginx працює, але портів немає:** перевір підключення `sites-enabled`, правильність `listen` та чи відбувся `reload`. Переглянь `sudo nginx -T` (увесь зібраний конфіг).

### 6.5. За потреби — локальний фаєрвол

Якщо на VM1 уже налаштований UFW і правила блокують підключення **з VM2**, можна дозволити **лише лабораторному клієнту**:

```bash
sudo ufw status verbose

# Виконувати ТІЛЬКИ якщо UFW активний і справді блокує порти:
sudo ufw allow from 192.168.106.20 to 192.168.106.10 port 8086 proto tcp
sudo ufw allow from 192.168.106.20 to 192.168.106.10 port 8449 proto tcp
```

Не вмикай UFW із нуля без розуміння наявних правил — це може зламати інші лабораторні сервіси.

## Крок 7. Додати **свій CA до довірених** на VM2 (пункт 2.6)

TLS-ланцюжок може бути криптографічно правильним, але `curl` усе одно скаже `certificate verify failed`, якщо клієнт **не довіряє CA**. Тому ми переносимо **тільки публічний сертифікат CA**, не його приватний ключ.

### 7.1. VM1 → VM2: передати публічний сертифікат

Якщо в ЛР3 він **уже є** на VM2 у `/etc/ssl/colorCA/certs/ca.cert.pem`, повторне копіювання не потрібне. Перевір:

```bash
# На VM2:
ls -l /etc/ssl/colorCA/certs/ca.cert.pem
```

Якщо файлу немає, на **VM1** (приклад через SCP за наявності SSH на VM2):

```bash
scp ~/ca/certs/ca.cert.pem <VM2_LINUX_USER>@192.168.106.20:/tmp/colorCA.crt
```

`<VM2_LINUX_USER>` заміни ім'ям свого **Linux-користувача VM2**, який може входити по SSH. Якщо SSH не налаштований, скористайся вже відпрацьованим у ЛР3 способом перенесення файлів. **Не переносити `ca.key.pem`.**

### 7.2. На VM2 — зареєструвати CA у системному trust store

Якщо CA із ЛР3 уже лежить на VM2 в `/etc/ssl/colorCA/certs/`:

```bash
sudo install -m 644 /etc/ssl/colorCA/certs/ca.cert.pem \
  /usr/local/share/ca-certificates/colorCA.crt
sudo update-ca-certificates
```

Або, якщо скопіював CA як `/tmp/colorCA.crt`:

```bash
sudo install -m 644 /tmp/colorCA.crt \
  /usr/local/share/ca-certificates/colorCA.crt
sudo update-ca-certificates
```

`.crt` — важливе розширення для Debian `update-ca-certificates` (сам вміст сертифіката залишається PEM).

> Якщо сертифікат **вже встановлено**, `update-ca-certificates` може не показати `1 added` — це нормально. Головна перевірка: TLS-сертифікат сайту проходить перевірку **без `-k`**.

### 7.3. Попередня перевірка CA на VM2

```bash
openssl x509 -in /usr/local/share/ca-certificates/colorCA.crt \
  -noout -subject -issuer
```

Публічний CA має назву `color CA`. Пізніше зробимо `curl` і `openssl s_client` через уже **запущений** HTTPS-сервер.

## Крок 8. Перевірити роботу HTTP через curl (VM2)

На цьому етапі **nginx має вже працювати**, а DNS `www.color.edu` повинен вести на `192.168.106.10`.

### 8.1. Перевірка DNS і доступності порту

```bash
getent ahostsv4 www.color.edu

# Чи відкривається TCP-з'єднання на HTTP-порт?
nc -vz 192.168.106.10 8086
```

`nc` має повідомити про успішне TCP-підключення. Це перевіряє **транспорт**, але ще **не HTTP і не пароль**.

### 8.2. Запит без логіна → очікуємо 401

```bash
curl --http1.1 -i http://www.color.edu:8086/
```

Очікувані ключові рядки (точні дати, версія nginx та порядок заголовків можуть різнитися):

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Basic realm="Lab7 - color.edu"
```

**Чому 401 — успіх?** Вебсайт доступний, nginx коректно **не віддає сторінку анонімному клієнту**. Це одна з основних вимог роботи.

Опції:

- `--http1.1` — явно вибрати HTTP/1.1 для зрозумілого аналізу;
- `-i` — вивести разом **з тілом** також HTTP-заголовки відповіді;
- `-I` — лише HTTP HEAD-запит (тіло за стандартом не надсилається);
- `-v` — детальний опис TCP/HTTP/TLS-обміну в stderr.

### 8.3. Правильний `red` → очікуємо 200

```bash
curl --http1.1 -i -u red http://www.color.edu:8086/
```

Введи **навчальний пароль red** після запиту `Enter host password ...`. Очікувано:

```http
HTTP/1.1 200 OK
Content-Type: text/html

<!DOCTYPE html>
<html lang="uk">
...
```

Текст HTML буде відповідати твоєму файлу `index.html`. `-u red` використовує HTTP Basic і інтерактивно запитає пароль (якщо не додати `:password`).

### 8.4. Перевірити всіх **трьох дозволених** користувачів

```bash
curl -i --http1.1 -u red    http://www.color.edu:8086/
curl -i --http1.1 -u greenu http://www.color.edu:8086/
curl -i --http1.1 -u blue   http://www.color.edu:8086/
```

Для кожного введи **його власний** пароль. Очікувано — `200 OK`.

### 8.5. Неправильний логін `green` і неправильний пароль → 401

```bash
# Користувача green немає в нашому htpasswd:
curl -i --http1.1 -u green http://www.color.edu:8086/

# Для red свідомо введи неправильний навчальний пароль:
curl -i --http1.1 -u red http://www.color.edu:8086/
```

Обидва тести **мають** завершитися `401 Unauthorized` (у другому тесті потрібно дійсно ввести неправильний пароль).

### 8.6. Підсумкова таблиця очікуваних результатів HTTP

| № | Запит | Очікуваний статус | Що доводить |
|---|---|---|---|
| 1 | Без `-u` | **401** | Анонімному клієнту доступ заборонено |
| 2 | `red`, правильний пароль | **200** | Користувач `red` працює |
| 3 | `greenu`, правильний пароль | **200** | Користувач `greenu` працює |
| 4 | `blue`, правильний пароль | **200** | Користувач `blue` працює |
| 5 | `green` замість `greenu` | **401** | Список точно відповідає 6-му варіанту |
| 6 | `red`, неправильний пароль | **401** | Автентифікація справді перевіряє пароль |
| 7 | Авторизований GET `/missing.html` | **404** | nginx не вигадує ресурси й перевіряє існування файлу |

Для останнього тесту:

```bash
curl -i --http1.1 -u red http://www.color.edu:8086/missing.html
```

Спочатку відбувається автентифікація, потім nginx шукає файл. **Без логіна** навіть запит неіснуючого файлу може повернути `401`, а не `404` — це нормально для захищеного сайту.

## Крок 9. Перевірити HTTPS і сертифікат CA (VM2)

Тепер переконуємось, що **не просто порт 8449 відкритий**, а саме **TLS-підпис, ім'я хоста та автентифікація коректні**.

### 9.1. TCP-порт HTTPS доступний

```bash
nc -vz 192.168.106.10 8449
```

Тільки TCP-доступність — **не доказ** правильного TLS.

### 9.2. Перевірити ланцюжок сертифікації й ім'я

```bash
openssl s_client \
  -connect www.color.edu:8449 \
  -servername www.color.edu \
  -verify_hostname www.color.edu \
  -CAfile /usr/local/share/ca-certificates/colorCA.crt \
  -brief </dev/null
```

За правильної роботи має бути інформація про узгоджену версію TLS та позитивну верифікацію (`Verification: OK` або еквівалентна позначка залежно від версії OpenSSL).

**Для чого всі параметри:**

| Опція | Навіщо |
|---|---|
| `-connect www.color.edu:8449` | Під'єднатись до адреси та порту HTTPS |
| `-servername www.color.edu` | Указати **SNI**, щоб сервер міг вибрати правильний сертифікат |
| `-verify_hostname www.color.edu` | Перевірити, що сертифікат призначений саме для цього імені |
| `-CAfile .../colorCA.crt` | Довіряти **нашому** CA із ЛР3 |
| `-brief` | Стислий режим інформації про TLS |
| `</dev/null` | Закрити стандартний ввід після перевірки, не чекати ручного введення |

**Важливо:** деякі параметри `s_client` можуть показувати діагностику навіть у разі проблеми. Найважливіше — **переконатися у позитивній перевірці**; якщо хочеш жорстко зупинити перевірку за помилки сертифіката, додай `-verify_return_error`.

### 9.3. HTTPS без пароля → 401, але **TLS успішний**

```bash
curl --http1.1 -v -i https://www.color.edu:8449/
```

Очікувано:

1. `curl` встановлює захищене TLS-з'єднання.
2. Перевірка сертифіката успішна (ознака на кшталт `SSL certificate verify ok`).
3. nginx відповідає **`401 Unauthorized`**, бо пароль ще не надано.

**Тут `401` — успіх двох незалежних підсистем:** TLS працює, а вебресурс закритий для анонімів.

### 9.4. HTTPS з авторизованим користувачем → 200

```bash
curl --http1.1 -i -u red https://www.color.edu:8449/
curl --http1.1 -i -u greenu https://www.color.edu:8449/
curl --http1.1 -i -u blue https://www.color.edu:8449/
```

Для кожного правильний навчальний пароль → **`200 OK`**, HTML-сторінка з ЛР7.

### 9.5. Неправильний користувач → 401

```bash
curl --http1.1 -i -u green https://www.color.edu:8449/
```

Очікувано: **`401 Unauthorized`**. Хоча `green` може бути Unix-користувачем із попередніх лабораторних, **він не є дозволеним веблогіном** у варіанті 6.

### 9.6. Чому не слід використовувати `curl -k`

```bash
# НЕ використовуйте так для головного доказу правильного HTTPS:
curl -k https://www.color.edu:8449/
```

`-k` / `--insecure` вимикає перевірку сертифіката, тож запит може «працювати» навіть із неправильним CA або ім'ям сервера. Для захисту потрібен **успішний curl БЕЗ `-k`**.

Якщо довіру ще налаштовуєш, можна тимчасово перевіряти так (це **не** `-k`, перевірка сертифіката залишається ввімкненою):

```bash
curl --cacert /usr/local/share/ca-certificates/colorCA.crt \
  -i -u red https://www.color.edu:8449/
```

Після `update-ca-certificates` бажано продемонструвати той самий результат уже **без `--cacert`**, користуючись системним trust store.

### 9.7. Матриця обов'язкових HTTPS-тестів

| № | HTTPS-запит | TLS-перевірка | HTTP-код |
|---|---|---|---|
| 1 | Без логіна | Успішна | **401** |
| 2 | `red` + правильний пароль | Успішна | **200** |
| 3 | `greenu` + правильний пароль | Успішна | **200** |
| 4 | `blue` + правильний пароль | Успішна | **200** |
| 5 | `green` (зайвий логін) | Успішна | **401** |
| 6 | `red` + неправильний пароль | Успішна | **401** |
| 7 | `openssl s_client` + перевірка імені/CA | **OK** | HTTP-запит не обов'язковий |

### 9.8. Що реально гарантує HTTPS

- **Конфіденційність:** сторонній спостерігач без ключів сеансу не бачить HTTP-тіло та `Authorization`.
- **Цілісність:** зміни зашифрованих повідомлень виявляються криптографічними механізмами TLS.
- **Автентифікація сервера:** клієнт перевіряє сертифікат, його SAN та довірений CA.
- **Не гарантує:** що вебсторінка не має вразливостей, що дозволений користувач нешкідливий, або що пароль сам по собі надійний.

## Крок 10. Надіслати HTTP-запит вручну через `telnet` або `netcat`

Це показує, що **HTTP/1.1 — зрозумілий текстовий протокол**, і для нього не обов'язково використовувати браузер.

### 10.1. Варіант `netcat` (зручніше для звіту)

**На VM2:**

```bash
printf 'GET / HTTP/1.1\r\nHost: www.color.edu:8086\r\nConnection: close\r\n\r\n' \
  | nc -w 3 192.168.106.10 8086
```

Очікуваний статус — **`401 Unauthorized`** з `WWW-Authenticate: Basic ...`, оскільки ми не надсилали `Authorization`.

**Розбір символів:** `\r\n` — CRLF, стандартне завершення рядка в HTTP/1.1. Два поспіль `\r\n` позначають **кінець заголовків**. Якщо забути фінальний порожній рядок, сервер може чекати продовження запиту.

### 10.2. Варіант `telnet`

```bash
telnet 192.168.106.10 8086
```

Введи вручну:

```http
GET / HTTP/1.1
Host: www.color.edu:8086
Connection: close

```

Після заголовка `Connection: close` **натисни Enter ще раз**, щоб завершити HTTP-заголовки. `telnet` може по-різному обробляти переноси рядків; для гарантованого `CRLF` краще `printf | nc`, як вище.

### 10.3. Чому такий самий `nc` **не працює** для HTTPS

Спроба передати відкритий текст `GET / HTTP/1.1` на **8449** не є TLS handshake. HTTPS-сервер чекає **TLS-повідомлення**, тому не повинен відповідати звичайним `200 OK` на сирий HTTP-потік.

Для ручної передачі HTTP **всередині TLS** використай:

```bash
printf 'GET / HTTP/1.1\r\nHost: www.color.edu:8449\r\nConnection: close\r\n\r\n' \
  | openssl s_client \
      -quiet \
      -connect www.color.edu:8449 \
      -servername www.color.edu \
      -verify_hostname www.color.edu \
      -verify_return_error \
      -CAfile /usr/local/share/ca-certificates/colorCA.crt
```

Очікується **`401`** (успішний TLS, але немає HTTP Basic-даних). Це красиво демонструє, що **в HTTPS всередині захищеного каналу — звичайний HTTP**.

## Крок 11. Практичне дослідження методів і заголовків HTTP

### 11.1. GET та HEAD — у чому різниця

```bash
# GET: заголовки + тіло сторінки
curl --http1.1 -i -u red http://www.color.edu:8086/

# HEAD: тільки заголовки, без HTML-тіла
curl --http1.1 -I -u red http://www.color.edu:8086/
```

Той самий приклад через HTTPS:

```bash
curl --http1.1 -I -u red https://www.color.edu:8449/
```

У HEAD можна побачити `Content-Type`, `Content-Length`, `Last-Modified`, `ETag`, `Cache-Control` (конкретний набір заголовків залежить від налаштувань та відповіді).

### 11.2. Принцип ідемпотентності та `POST`

Наш сайт **статичний**; сервер не має API для обробки POST. Тому:

```bash
curl -i --http1.1 -u red \
  -X POST -d 'message=hello' \
  http://www.color.edu:8086/
```

Після успішної автентифікації nginx для статичного ресурсу зазвичай відповість **`405 Method Not Allowed`** — це очікувана поведінка **саме нашої конфігурації**, не означає, що HTTP узагалі не підтримує POST.

### 11.3. `Cache-Control`, ETag і умовні запити

```bash
curl --http1.1 -I -u red https://www.color.edu:8449/
```

Подивись, чи є `Cache-Control: no-store` — це наш свідомий вибір для захищеної сторінки. Для статичного файлу nginx зазвичай також надає `Last-Modified` та `ETag`.

Якщо ETag з'явився, вручну використай його **точне фактичне значення** в умовному запиті:

```bash
# ЗАМІНИ <ЕТАГ_ІЗ_ПОПЕРЕДНЬОЇ_ВІДПОВІДІ> на фактичне значення,
# включно з лапками навколо значення ETag.
# Приклад синтаксису: -H 'If-None-Match: "вміст-з-ETag"'

curl --http1.1 -i -u red \
  -H 'If-None-Match: "ВСТАВ_РЕАЛЬНИЙ_ETAG"' \
  https://www.color.edu:8449/
```

Якщо значення **точно збігається**, можливий `304 Not Modified` (без тіла). `Cache-Control: no-store` усе одно забороняє кешу зберігати відповідь для майбутнього використання; це **ручна перевірка умовного HTTP-запиту**, а не вимога створити реальний кеш.

### 11.4. Продемонструвати Keep-Alive

```bash
curl --http1.1 -v -u red \
  -o /dev/null https://www.color.edu:8449/ \
  -o /dev/null https://www.color.edu:8449/
```

Шукай у verbose-виводі повідомлення на кшталт `Re-using existing connection` (формулювання залежить від версії curl): клієнт може перевикористати той самий TCP/TLS канал для двох послідовних запитів.

**Не плутати:** кілька HTTP-запитів на одному TCP-з'єднанні **не означають**, що сервер зберігає сесію користувача через cookies. Це лише повторне використання **транспортного каналу**.

## Крок 12. Аналіз мережного обміну HTTP та HTTPS (пункт 2.3)

**Потрібно отримати не лише статус 200, а й показати, що саме летить мережею.** Робимо два окремі дампи — для HTTP і для HTTPS. Нижче `enp0s8` — Host-only-інтерфейс; якщо у тебе інша назва, заміни її.

### 12.1. Дамп HTTP: на VM1 почати запис

```bash
sudo tcpdump -i enp0s8 -nn -s 0 \
  -w /tmp/lab7-http.pcap \
  'host 192.168.106.20 and tcp port 8086'
```

Пояснення:

- `-i enp0s8` — перехоплювати на Host-only мережі;
- `-nn` — не перетворювати адреси/порти на імена;
- `-s 0` — записувати повні доступні пакети без навмисного обрізання;
- `-w` — зберігати в **PCAP**, який зручно відкрити у Wireshark;
- фільтр — тільки TCP-трафік між VM1/VM2 на HTTP-порту `8086`.

**Поки tcpdump працює**, на VM2 виконай:

```bash
# 1) без логіна (401)
curl --http1.1 -i http://www.color.edu:8086/

# 2) із правильним логіном (200)
curl --http1.1 -i -u red http://www.color.edu:8086/
```

Зупини `tcpdump` через **Ctrl+C**. Файл `/tmp/lab7-http.pcap` збережений на VM1.

### 12.2. Аналіз HTTP-дампа

Швидкий текстовий перегляд **тільки у власній лабораторній**:

```bash
sudo tcpdump -nn -A -r /tmp/lab7-http.pcap 'tcp port 8086' | less
```

Важливо: у відкритому HTTP `Authorization: Basic ...` передається **без шифрування**, тому дамп може містити **ваші навчальні паролі у декодованій формі після Base64**. Не публікуй такий `.pcap` у відкритий доступ і **не вставляй самі облікові дані у звіт**.

У Wireshark фільтр відображення:

```text
http && tcp.port == 8086
```

На що звернути увагу:

| Елемент | Що побачимо |
|---|---|
| TCP handshake | `SYN`, `SYN,ACK`, `ACK` |
| `GET / HTTP/1.1` | Метод і шлях |
| `Host: www.color.edu:8086` | Ім'я сайту, до якого звернувся клієнт |
| `401 Unauthorized` | Відсутність валідної автентифікації |
| `WWW-Authenticate: Basic realm="..."` | Виклик автентифікації сервером |
| `Authorization: Basic ...` | Дані користувача у вигляді Base64 (**не розкривати їх у звіті**) |
| `200 OK` | Успішна відповідь авторизованому користувачу |
| `Content-Type: text/html` | Тип тіла відповіді |
| HTML після заголовків | **Видимий у відкритому вигляді** в HTTP-дампі |

Для звіту можна зробити скріншоти **пакетів `GET`, `401`, `200` і заголовків** із **замаскованим `Authorization`**. Якщо видаляєш секрет зі скріншота, переконайся, що він не залишився в іншій ділянці кадру або у файлі дампа, який збираєшся передавати.

### 12.3. Дамп HTTPS: запис TLS-трафіку

На **VM1**:

```bash
sudo tcpdump -i enp0s8 -nn -s 0 \
  -w /tmp/lab7-https.pcap \
  'host 192.168.106.20 and tcp port 8449'
```

Поки запис триває, на **VM2**:

```bash
curl --http1.1 -v -i https://www.color.edu:8449/
curl --http1.1 -v -i -u red https://www.color.edu:8449/
```

Зупини `tcpdump` через **Ctrl+C**.

### 12.4. Аналіз HTTPS-дампа

У Wireshark:

```text
tcp.port == 8449
```

Якщо розпізнавання TLS не відбулося автоматично, вибери для TCP-потоку **Decode As → TLS**. Тепер зверни увагу на:

| Що видно | Що означає |
|---|---|
| TCP handshake | Перед TLS завжди встановлюється TCP-з'єднання (для нашого HTTPS) |
| TLS `ClientHello` | Клієнт пропонує TLS-параметри; за звичайних умов видно SNI `www.color.edu` |
| TLS `ServerHello` | Сервер обирає параметри протоколу |
| TLS Application Data | Зашифровані повідомлення; звичайний `GET /` не читається напряму |
| `Certificate` | У TLS 1.2 може бути видимим; у TLS 1.3 зазвичай уже захищене шифруванням |

**Головний висновок із порівняння:**

```text
HTTP :  можеш побачити GET, Host, Authorization і HTML у дампі.
HTTPS: після TLS handshake не бачиш звичайних GET/Authorization/HTML
       без спеціальних ключів сеансу для дешифрування.
```

**Важливе уточнення:** HTTP/HTTPS мають **ті самі методи й статус-коди**, але в HTTPS сторонньому спостерігачеві вони приховані шифруванням TLS. Вони **не зникають**, просто не зчитуються з PCAP у відкритому вигляді.

### 12.5. Аналіз TLS-сертифіката — окремо від PCAP

На VM2:

```bash
openssl s_client \
  -connect www.color.edu:8449 \
  -servername www.color.edu \
  -verify_hostname www.color.edu \
  -CAfile /usr/local/share/ca-certificates/colorCA.crt \
  -showcerts </dev/null
```

У виводі перевір:

- сертифікат виданий **для `www.color.edu`**;
- Issuer — **`color CA`**;
- TLS узгоджено, з'єднання не відкинуто;
- `Verify return code: 0 (ok)` або аналогічну позитивну позначку.

> **Чому не можна вимагати однаковий набір TLS-повідомлень у всіх?** TLS 1.2/1.3, повторні з'єднання, session resumption, версії curl, nginx і Wireshark впливають на те, які поля видно в дампі. Висновок повинен ґрунтуватися на фактично перехоплених пакетах.

## Крок 13. Журнали nginx і фінальна діагностика

### На VM1

```bash
# Усі запити HTTP/HTTPS, де видно час, клієнта, URL і код статусу
sudo tail -n 30 /var/log/nginx/color-http.access.log
sudo tail -n 30 /var/log/nginx/color-https.access.log

# Помилки nginx
sudo tail -n 30 /var/log/nginx/color-http.error.log
sudo tail -n 30 /var/log/nginx/color-https.error.log

# Перевірити, що конфіг синтаксично коректний
sudo nginx -t

# Слухання портів
sudo ss -lntp | grep -E ':(8086|8449)\b'
```

**Що можна довести журналами:** успішні запити (код `200`), спроби доступу без пароля (`401`), неіснуючі ресурси (`404`). За замовчуванням access_log nginx **не повинен** записувати сам заголовок `Authorization`; не змінюй формат журналу так, щоб туди випадково потрапили секрети.

# ЧАСТИНА 4. КОНТРОЛЬНІ ПИТАННЯ — РОЗГОРНУТІ ВІДПОВІДІ

Нижче — **усі сім питань із пункту 3 методички `07.pdf`**, із прикладами **саме нашої лабораторної**.

## 3.1. Протокол HTTP

**HTTP (Hypertext Transfer Protocol)** — прикладний протокол обміну повідомленнями між клієнтом і вебсервером за моделлю **request/response**. Клієнт надсилає запит із методом (наприклад, `GET`), адресою ресурсу, версією протоколу та заголовками; сервер повертає відповідь із кодом статусу, заголовками й, за потреби, тілом.

**Характеристики:**

- Орієнтований на ресурси: один ресурс може бути доступним за URI й мати різні представлення.
- **Stateless**: протокол не вимагає зберігати стан користувача між запитами.
- Розширюваний через заголовки, методи й узгодження вмісту.
- **HTTP/1.1** традиційно працює поверх TCP; **HTTPS у цій лабораторній — HTTP поверх TLS поверх TCP**.
- HTTP/2/3 мають новий спосіб передачі кадрів, але спільну HTTP-семантику.

**Наш приклад:** `curl` (VM2) запитує `http://www.color.edu:8086/`; nginx (VM1) без авторизації повертає `401`, з правильними даними `red`/`greenu`/`blue` — `200 OK` з HTML.

**Ключовий момент на захисті:** **HTTP — протокол, а nginx — його програмна реалізація.** DNS, TCP і TLS — окремі компоненти, які допомагають HTTP дістатися до потрібного сервера або захистити передавання.

## 3.2. Покажчики ресурсів URI та URL

**URI** — загальний ідентифікатор ресурсу. **URL** — URI, що визначає місце або спосіб доступу до ресурсу. Наше `https://www.color.edu:8449/` — водночас URI і URL.

```text
https://www.color.edu:8449/index.html?theme=dark#footer
|https|      host     |port|   path     |query    |fragment|
```

- `https` — схема звернення;
- `www.color.edu` — доменне ім'я вебсервера;
- `8449` — нестандартний порт HTTPS;
- `/index.html` — шлях ресурсу;
- `theme=dark` — query-параметр;
- `footer` — фрагмент документа; до сервера не передається.

**Практична відмінність:** DNS визначає **IP вузла**, але **не знає**, що таке `/index.html`, який порт `8449` використовує сайт чи який fragment у посиланні. URL розбирає клієнт, який уже визначає, як саме встановити з'єднання й що запитати.

## 3.3. Структура повідомлень HTTP

**HTTP/1.1-запит** складається зі стартового рядка, заголовків, порожнього рядка, необов'язкового тіла:

```http
GET / HTTP/1.1
Host: www.color.edu:8086
Accept: text/html

```

**HTTP/1.1-відповідь** складається з рядка статусу, заголовків, порожнього рядка, необов'язкового тіла:

```http
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 124

<html> ... </html>
```

Часто важливі заголовки:

| Запит | Відповідь |
|---|---|
| `Host` — ім'я сервера | `Content-Type` — MIME-тип ресурсу |
| `Authorization` — автентифікаційні дані | `WWW-Authenticate` — яку автентифікацію вимагає сервер |
| `Accept` — прийнятні типи | `Content-Length` — розмір тіла |
| `If-None-Match` — умовний запит | `ETag` — версія представлення |
| `Cookie` — клієнт надсилає стан | `Set-Cookie` — сервер задає cookie |
| `Connection` — керування з'єднанням HTTP/1.1 | `Cache-Control` — правила кешування |

**Що показати:** `printf 'GET / HTTP/1.1\r\nHost: ...\r\n\r\n' | nc ...` або `curl -v`, а також HTTP-пакети з Wireshark. Вміст між початковим рядком і порожнім рядком — **заголовки**, а все далі — **тіло**, якщо воно є.

## 3.4. Методи HTTP

Метод описує **намір** клієнта щодо ресурсу.

| Метод | Використання |
|---|---|
| `GET` | Отримати ресурс; зазвичай не змінює стан |
| `HEAD` | Отримати лише метадані відповіді, без тіла |
| `POST` | Надіслати дані для обробки, часто створити новий ресурс |
| `PUT` | Замінити представлення ресурсу за конкретним URI |
| `PATCH` | Частково змінити ресурс |
| `DELETE` | Видалити ресурс |
| `OPTIONS` | Дізнатись підтримувані параметри комунікації |
| `TRACE` | Діагностика, у практиці часто вимкнений |
| `CONNECT` | Побудова тунелю через проксі |

**Важливі поняття:**

- **Safe** — метод за визначенням **не вимагає** зміни стану (наприклад, `GET`, `HEAD`).
- **Idempotent** — багато однакових запитів мають такий самий бажаний ефект, що й один (`PUT`, `DELETE`, `GET`, `HEAD`).
- `POST` загалом **не ідемпотентний**, бо два запити можуть створити два замовлення.

**Наш дослід:** `GET /` → `200`, `HEAD /` → `200` **без HTML-тіла**, `POST /` у статичному nginx може → `405` (відсутній застосунок, який обробляє POST). Це не помилка HTTP.

## 3.5. Сесії в протоколі HTTP

HTTP **за замовчуванням не пам'ятає**, хто надсилав попередній запит. Щоб застосунок «пам'ятав» користувача, використовують **cookies і серверний session store**, токени або повторну автентифікацію.

```text
HTTP session через cookie:
1) POST /login        → Set-Cookie: session_id=abc
2) GET /profile       → Cookie: session_id=abc
3) Сервер за abc      → знаходить дані конкретного користувача
```

У нашій лабораторній nginx використовує **Basic Authentication**, коли клієнт надсилає `Authorization: Basic ...`. **Cookie-сесію ми не створюємо**. Браузер може запам'ятати введені облікові дані та надсилати їх знову, але це інше, ніж серверна сесія вебзастосунку.

**Не плутати з TCP Keep-Alive.** Кілька HTTP-запитів можуть використовувати одне TCP-з'єднання, але це не змінює stateless-семантику HTTP.

## 3.6. Кешування в протоколі HTTP

**Кешування** — збереження відповіді з метою повторного використання, щоб не просити сервер повторно відправляти незмінну інформацію.

**Основні керівні заголовки:**

- `Cache-Control: max-age=60` — відповідь може бути свіжою 60 секунд за правилами кешу.
- `Cache-Control: private` — відповідь не для спільних кешів.
- `Cache-Control: no-cache` — кеш може **зберігати**, але перед використанням має **валідувати**.
- `Cache-Control: no-store` — **не зберігати** в кеші.
- `ETag` + `If-None-Match` — перевірка зміни вмісту.
- `Last-Modified` + `If-Modified-Since` — перевірка за часом модифікації.

```text
GET /file → 200 OK, ETag: "v7"
GET /file, If-None-Match: "v7" → 304 Not Modified
```

**Застосування в ЛР7:** на захищених HTTP/HTTPS-сторінках nginx встановлює `Cache-Control: no-store`, що краще для навчального прикладу з автентифікацією. Поняття `304` і ETag розглядаємо теоретично або демонструємо вручну з фактичним ETag.

**Чому не лише швидкість:** спільне неправильне кешування персональних даних може спричинити витік. Тому треба розуміти відмінність `public`, `private`, `no-cache` й `no-store`.

## 3.7. Постійне з'єднання в протоколі HTTP

**Persistent connection (Keep-Alive)** дозволяє передавати **декілька HTTP-запитів через одне TCP-з'єднання** без повторного встановлення TCP після кожної відповіді.

У **HTTP/1.1** постійне з'єднання типово використовується автоматично; явний заголовок `Connection: close` або тайм-аут закривають його. Сервер може закрити з'єднання з інших причин. Завершення **одного HTTP-запиту** не означає обов'язкового завершення **TCP-сесії**.

```text
TCP handshake
  ├── GET /index.html → 200
  ├── GET /style.css  → 200
  └── закриття з'єднання
```

**Переваги:** менше TCP handshakes, менші затримки, нижчі накладні витрати. Для HTTPS повторне використання також зменшує кількість повних TLS handshakes.

**Наш дослід:** два послідовні URL для `curl --http1.1 -v ...` можуть дати повідомлення про повторне використання існуючого з'єднання; у PCAP можна перевірити, чи обидва GET належали одному TCP-потоку.

| `SSL certificate problem: unable to get local issuer certificate` | CA не доданий до довірених VM2 | `update-ca-certificates`, `openssl s_client -CAfile ...` |
| `no alternative certificate subject name matches ...` | Сертифікат **без правильного SAN** або URL-ім'я відрізняється | `openssl x509 -ext subjectAltName`, перевипустити через CA із SAN |
| `certificate has expired` / `not yet valid` | Сертифікат або годинник VM | `date -u`, `openssl x509 -dates`, синхронізація часу |
| TLS handshake fail | Ключ не відповідає сертифікату, проблема протоколу, неверний конфіг | `nginx -t`, `journalctl -u nginx`, `openssl s_client` |
| `curl -k` працює, звичайний `curl` ні | TLS-сервер доступний, але **довіра/ім'я не пройшли** | Правильно встановити CA + SAN, **не залишати `-k`** |
| `www.color.edu` не відкривається без порту | Порти нестандартні, не 80 і 443 | Використовувати `:8086` або `:8449` |
| `tcpdump` нічого не бачить | Не той інтерфейс, не той порт, трафік іде через NAT/loopback | `ip -br addr`, фільтр `port 8086` / `8449` |
| HTTPS PCAP не показує `GET` | **Так і має бути**, якщо HTTP захищено TLS | Порівняй із відкритим HTTP; подивись TLS Application Data |
| `POST` повернув 405 | Статичний nginx не має обробника POST | Це очікувано, не вимога налаштовувати API |
| `htpasswd -cB` стер інших користувачів | `-c` **створює файл із нуля** | Створювати з `-c` лише першого; наступні — без `-c` |
| Сертифікат підписано не `color CA` | Використано інший CA або `openssl req -x509` | Порівняй `issuer`, `openssl verify`, підписати CSR через CA із ЛР3 |

## 5.1. Послідовність пошуку помилки (від нижнього рівня до верхнього)

```text
1. Мережа:      ip addr, ping до 192.168.106.10
      ↓
2. DNS:         dig @192.168.106.10 www.color.edu A
      ↓
3. OS resolver:  getent ahostsv4 www.color.edu
      ↓
4. TCP:         nc -vz 192.168.106.10 8086 / 8449
      ↓
5. nginx:       nginx -t, ss, error.log
      ↓
6. HTTP:        curl -i без логіна → 401
      ↓
7. Basic Auth:  curl -i -u red → 200
      ↓
8. TLS:         openssl s_client + перевірка SAN і CA
      ↓
9. HTTPS:       curl БЕЗ -k → 401 / 200
      ↓
10. PCAP:       tcpdump і порівняння HTTP/HTTPS
```

Це набагато швидше, ніж при кожній проблемі одразу перевстановлювати nginx.

## Що відповідати на популярні запитання викладача

**Чому `8086` і `8449`, а не `80` та `443`?** — Це **спеціальні порти мого 6-го варіанту**. У TCP з'єднання визначають IP і порт, тому без явного порту в URL клієнт піде на стандартні `80`/`443`, а не на наші.

**Навіщо DNS, якщо IP відомий?** — Щоб клієнт звертався за заданим у варіанті **доменним ім'ям**; воно також потрібне для TLS-перевірки SAN. IP можна обійти через `--resolve` лише для діагностики.

**Чому `401` без пароля — це добре?** — Так вебсервер показує, що ресурс **захищений**. З правильним паролем має бути `200`, а не `401`.

**Чим Basic відрізняється від шифрування?** — Basic передає `username:password` у Base64, а Base64 можна легко розкодувати. **Лише TLS захищає обмін** від стороннього читання в мережі.

**Навіщо CA із ЛР3?** — Лабораторна явно вимагає **використати створений раніше CA для підпису нового серверного сертифіката**. VM2 довіряє публічному CA-сертифікату, тому перевіряє підпис вебсервера.

**Що таке CSR?** — Запит на видачу сертифіката, що включає публічний ключ і дані заявника, та підписується відповідним приватним ключем. CA перевіряє й підписує сертифікат.

**Навіщо SAN, коли є CN?** — Сучасні клієнти використовують **SAN** для перевірки DNS-імен. Тому в сертифікаті має бути `DNS:www.color.edu`.

**Чому `curl -k` — поганий доказ?** — Тому що `-k` **ігнорує перевірку** сертифіката. Справжня успішна перевірка HTTPS — це запит **без `-k`**, із довірою до CA та правильним ім'ям.

**Чому у HTTPS-дампі не видно GET?** — Тому що HTTP-повідомлення передається **всередині шифрованого TLS**, хоча HTTP як прикладний протокол нікуди не зник.

**Що таке Keep-Alive?** — Здатність провести **кілька HTTP-запитів на одному TCP-з'єднанні**, щоб не повторювати TCP/TLS-узгодження для кожного ресурсу.

**Що таке cookies?** — Додатковий механізм збереження логічного стану користувача між окремими HTTP-запитами. У нашій роботі **немає cookie-сесій**, лише Basic Authentication.

**Чому логін `green` не проходить?** — У завданні **саме `greenu`**, це окремий вебкористувач у файлі `.htpasswd`.
