# ЧАСТИНА 1. ТЕОРІЯ

## 1.1. Навіщо потрібен DNS

Людині зручно працювати з іменами (`comsys.kpi.ua`), а стеку TCP/IP потрібні IP-адреси (`192.168.22.10`). DNS (Domain Name System) — це розподілена ієрархічна база даних, яка виконує **перетворення імен в адреси** (пряме перетворення) і **адрес в імена** (зворотне перетворення), а також зберігає службову інформацію про домен (поштові сервери, службові записи тощо).

До DNS використовувався один файл `hosts.txt`, який централізовано розповсюджувався на всі вузли ARPANET. Такий підхід не масштабувався: файл треба завантажувати повністю, імена мусили бути унікальними глобально, а зміни доходили з великою затримкою. DNS вирішує ці проблеми трьома ідеями:

1. **Ієрархічний простір імен** — унікальність забезпечується локально в межах домену.
2. **Делегування** — кожен власник домену сам відповідає за свою частину бази.
3. **Кешування** — відповіді зберігаються тимчасово, що різко зменшує навантаження.

Базові документи: **RFC 1034** (концепції) та **RFC 1035** (реалізація і формати).

## 1.2. Простір доменних імен

Простір імен — перевернуте дерево:

```
                        .            (корінь, root)
          ┌─────────────┼─────────────┐
         ua            com           edu      ← TLD (top-level domains)
          │                           │
         kpi                        color     ← домени 2-го рівня
          │                           │
       comsys                    red green    ← вузли / піддомени
```

* **FQDN (Fully Qualified Domain Name)** — повне ім'я від вузла до кореня, із крапкою в кінці: `red.color.edu.` Крапка в кінці — це і є корінь. У файлах зон BIND ця крапка **критично важлива** (див. п. 1.9).
* **Мітка (label)** — частина між крапками, до 63 символів; повне ім'я — до 255 символів.
* Типи TLD: gTLD (`com`, `net`, `org`, `edu`), ccTLD (`ua`, `pl`, `de`), спеціальний `arpa` (службовий, для зворотних зон).

## 1.3. Домен і зона — це різні речі

* **Домен** — уся піддеревина простору імен, включно з усіма піддоменами.
* **Зона** — та частина домену, за яку **адміністративно відповідає конкретний сервер**, тобто набір записів, які фізично лежать у файлі зони.

Приклад: домен `color.edu` може містити піддомен `lab.color.edu`. Якщо цей піддомен **делеговано** іншому серверу, то зона `color.edu` вже не містить даних `lab.color.edu` — у ній залишаються тільки NS-записи, що вказують, кому делеговано. Якщо делегування немає — домен і зона збігаються (саме такий випадок у нашій лабораторній).

**Делегування** — це запис типу NS у батьківській зоні, що вказує на сервери дочірньої зони, плюс (за потреби) «клейові» A-записи (glue records), якщо сервер дочірньої зони знаходиться всередині самої дочірньої зони.

## 1.4. Типи DNS-серверів

**За джерелом даних:**

* **Авторитетний (authoritative)** — сервер, що має власну копію зони і дає на неї відповіді з прапорцем `aa` (authoritative answer).
  * **Первинний / master / primary** — зберігає зону у вигляді файлу, який редагує адміністратор. Єдине місце внесення змін.
  * **Резервний / slave / secondary** — отримує копію зони від первинного механізмом **transfer** і зберігає її локально. Відповідає теж авторитетно. Потрібен для відмовостійкості й розподілу навантаження. RFC вимагає мінімум два NS для зони.
* **Кешуючий / recursive resolver** — не має власних зон, виконує запити від імені клієнта та кешує результат (типовий «DNS-сервер провайдера», 8.8.8.8 тощо).
* **Forwarding (перенаправляючий)** — не робить повний обхід ієрархії, а пересилає запити «вище», на вказаний forwarder.
* **Кореневі (root) сервери** — 13 логічних серверів (a…m.root-servers.net), знають лише делегування TLD. Їхні адреси «зашиті» в кожен резолвер у файлі підказок (`root.hints` / `db.root`).

**Stub-resolver** — клієнтська бібліотека ОС (налаштовується через `/etc/resolv.conf`), яка сама ієрархію не обходить, а звертається до рекурсивного сервера.

## 1.5. Рекурсивний та ітеративний режими

* **Рекурсивний запит**: клієнт каже «дай мені остаточну відповідь». Сервер зобов'язаний або знайти відповідь (сам опитавши інші сервери), або повернути помилку. Прапорець `RD` (Recursion Desired) в запиті, `RA` (Recursion Available) у відповіді.
* **Ітеративний запит**: сервер відповідає тим, що знає: або відповіддю з кешу/зони, або **посиланням (referral)** на сервери, які знають більше.

**Повна процедура перетворення `red.color.edu` в IP** (відповідь на контрольне питання 4.5):

1. Застосунок викликає `getaddrinfo()`; stub-resolver перевіряє `/etc/hosts` та кеш.
2. Stub-resolver відправляє **рекурсивний** запит на сервер із `/etc/resolv.conf`.
3. Рекурсивний сервер перевіряє свій кеш. Якщо немає — звертається **ітеративно** до кореневого сервера.
4. Корінь відповідає referral'ом: «за `edu` відповідають такі-то NS».
5. Сервер `edu` відповідає referral'ом: «за `color.edu` відповідають ns1/ns2».
6. `ns1.color.edu` відповідає авторитетно: `red.color.edu A 192.168.22.10`.
7. Рекурсивний сервер кешує відповідь на час TTL і віддає її клієнту.

## 1.6. Формат ресурсного запису (RR)

```
<ім'я>   [TTL]   <клас>   <тип>   <дані>
red       3600     IN       A      192.168.22.10
```

* **ім'я** — власник запису; якщо порожнє — успадковується від попереднього рядка.
* **TTL** — час життя в кеші (секунди). Якщо не вказано — береться з `$TTL`.
* **клас** — практично завжди `IN` (Internet).
* **тип** — визначає зміст поля даних.

### Основні типи записів

| Тип | Призначення |
|---|---|
| **SOA** | Start of Authority — початок зони, її параметри. Обов'язковий, рівно один на зону, завжди перший. |
| **NS** | Name Server — авторитетні сервери зони. Мінімум один (реально — два). |
| **A** | ім'я → IPv4-адреса. |
| **AAAA** | ім'я → IPv6-адреса. |
| **CNAME** | канонічне ім'я, тобто **псевдонім (alias)**: `ws1 → red`. |
| **PTR** | адреса → ім'я (використовується у зворотній зоні). |
| **MX** | поштовий сервер домену + пріоритет. |
| **TXT** | довільний текст (SPF, DKIM, верифікація). |
| **SRV** | розташування служби (протокол, порт, пріоритет, вага). |

### SOA детально

```
@ IN SOA ns1.color.edu. admin.color.edu. (
        2026092001 ; Serial
        3600       ; Refresh
        900        ; Retry
        604800     ; Expire
        86400 )    ; Negative Cache TTL (Minimum)
```

* **MNAME** (`ns1.color.edu.`) — ім'я первинного сервера зони.
* **RNAME** (`admin.color.edu.`) — пошта адміністратора, де перша крапка замінює `@` (тобто `admin@color.edu`).
* **Serial** — серійний номер зони. **Slave оновлює зону тільки якщо serial на master'і більший.** Якщо забути його збільшити — зміни не доїдуть на резервний сервер. Конвенція: `YYYYMMDDNN`.
* **Refresh** — через який інтервал slave перевіряє serial у master'а.
* **Retry** — інтервал повтору, якщо master недоступний.
* **Expire** — через скільки slave вважає свою копію недійсною і перестає відповідати по зоні.
* **Minimum / Negative TTL** — час кешування **негативних** відповідей (NXDOMAIN).

### Правила для CNAME (часте джерело помилок)

* У вузла з CNAME **не може бути інших записів** (ні A, ні MX, ні TXT).
* CNAME **не можна** використовувати в правій частині NS та MX (формально заборонено).
* На вершині зони (`@`) CNAME неприпустимий — там уже є SOA і NS.
* CNAME може вказувати на інший CNAME (ланцюжок), але це не рекомендується.

## 1.7. Зворотна зона та in-addr.arpa

Щоб перетворення «адреса → ім'я» вписалось у ту саму ієрархію, IP-адресу записують **у зворотному порядку** октетів і додають суфікс `in-addr.arpa`:

```
192.168.22.10  →  10.22.168.192.in-addr.arpa.  →  PTR  red.color.edu.
```

Порядок перевернуто, бо в IP-адресі старша (загальніша) частина — зліва, а в доменному імені загальніша частина — справа. Для мережі /24 зона називається `22.168.192.in-addr.arpa`. Для IPv6 аналогічно використовується `ip6.arpa` із півбайтовою нотацією.

## 1.8. Передача зон (zone transfer), NOTIFY, кешування

* **AXFR** — повна передача зони. Виконується поверх **TCP/53** (бо обсяг даних перевищує UDP-датаграму).
* **IXFR** — інкрементальна передача, лише зміни (RFC 1995).
* **NOTIFY** (RFC 1996) — master одразу повідомляє slave про зміну зони, щоб не чекати `Refresh`.
* Алгоритм на slave: за таймером Refresh (або після NOTIFY) запитує SOA у master'а → порівнює Serial → якщо більший, ініціює AXFR/IXFR.
* З міркувань безпеки передачу обмежують: `allow-transfer { IP-резервного; };` Інакше будь-хто може викачати всю структуру мережі.

**Кешування** (питання 4.6): будь-який резолвер зберігає отримані записи на час TTL, зазначений власником зони. Це зменшує затримку і навантаження на авторитетні сервери, але створює затримку поширення змін — тому перед плановою зміною TTL заздалегідь зменшують. Кешуються також і негативні відповіді (NXDOMAIN) — на час Minimum із SOA.

## 1.9. BIND9: структура конфігурації

Пакет: `bind9`, служба в Debian 12: `named.service` (аліас `bind9.service`).

| Файл | Призначення |
|---|---|
| `/etc/bind/named.conf` | головний файл, підключає три наступні |
| `/etc/bind/named.conf.options` | глобальні опції (рекурсія, listen-on, forwarders) |
| `/etc/bind/named.conf.local` | **опис наших зон** |
| `/etc/bind/named.conf.default-zones` | localhost, зворотна для 127.0.0.1, root hints |
| `/var/cache/bind/` | робочий каталог; сюди slave пише отримані зони |
| `/var/log/syslog`, `journalctl -u named` | логи |

Синтаксис файлу зони:

* `$TTL 3600` — TTL за замовчуванням, має бути на початку.
* `$ORIGIN color.edu.` — суфікс, який дописується до всіх **відносних** імен. Якщо не вказано — береться ім'я зони з `named.conf`.
* `@` — скорочення для поточного `$ORIGIN` (вершина зони).
* **Ім'я без крапки в кінці — відносне**, до нього дописується `$ORIGIN`. Ім'я з крапкою — абсолютне.
  * `red IN A ...` → `red.color.edu.`
  * `ns1.color.edu IN A ...` (без крапки!) → `ns1.color.edu.color.edu.` — класична помилка.
* `;` — коментар.

Утиліти перевірки:

```bash
named-checkconf                      # синтаксис конфігурації
named-checkzone color.edu /etc/bind/zones/db.color.edu   # синтаксис зони
rndc reload                          # перечитати зони без перезапуску
rndc retransfer color.edu            # примусово перезабрати зону (на slave)
```

## 1.10. Діагностичні утиліти

**dig** — основний інструмент, показує повну відповідь сервера:

```bash
dig @192.168.106.10 red.color.edu A        # запит конкретного типу до конкретного сервера
dig @192.168.106.10 color.edu SOA
dig @192.168.106.10 color.edu NS
dig @192.168.106.10 -x 192.168.22.10       # зворотний запит (PTR)
dig @192.168.106.10 color.edu AXFR         # спроба передачі зони
dig +short red.color.edu                   # лише відповідь
dig +trace red.color.edu                   # покроковий обхід ієрархії
dig +norecurse @192.168.106.20 color.edu SOA  # перевірка авторитетності
```

У виводі важливі: `status: NOERROR/NXDOMAIN`, прапорці `aa` (авторитетна відповідь), `ra`, секції `ANSWER/AUTHORITY/ADDITIONAL`.

**host** — короткий вивід: `host red.color.edu 192.168.106.10`
**nslookup** — інтерактивний режим:

```
nslookup
> server 192.168.106.10
> set type=any
> color.edu
> exit
```

## Крок 3. Налаштування VM1 (первинний сервер)

### 3.1. Глобальні опції

```bash
sudo cp /etc/bind/named.conf.options /etc/bind/named.conf.options.bak
sudo nano /etc/bind/named.conf.options
```

```conf
acl "trusted" {
        127.0.0.1;
        192.168.106.0/24;
};

options {
        directory "/var/cache/bind";

        // рекурсія дозволена лише для нашої лабораторної мережі
        recursion yes;
        allow-query { trusted; };
        allow-recursion { trusted; };

        // куди пересилати запити щодо зовнішніх доменів
        forwarders {
                8.8.8.8;
                1.1.1.1;
        };

        // наші зони не підписані DNSSEC, валідацію вимикаємо,
        // щоб уникнути SERVFAIL у лабораторному середовищі
        dnssec-validation no;

        listen-on { 127.0.0.1; 192.168.106.10; };
        listen-on-v6 { none; };
};
```

> На VM2 у цьому ж файлі в `listen-on` треба буде вказати `192.168.106.20`.

### 3.2. Опис зон

Створимо окремий каталог для файлів зон:

```bash
sudo mkdir -p /etc/bind/zones
```

```bash
sudo nano /etc/bind/named.conf.local
```

```conf
// ---------- ПРЯМА ЗОНА 1 ----------
zone "color.edu" {
        type master;
        file "/etc/bind/zones/db.color.edu";
        allow-transfer { 192.168.106.20; };
        also-notify { 192.168.106.20; };
        notify yes;
};

// ---------- ПРЯМА ЗОНА 2 ----------
zone "zone06.net" {
        type master;
        file "/etc/bind/zones/db.zone06.net";
        allow-transfer { 192.168.106.20; };
        also-notify { 192.168.106.20; };
        notify yes;
};

// ---------- ЗВОРОТНА ЗОНА для 192.168.22.0/24 ----------
zone "22.168.192.in-addr.arpa" {
        type master;
        file "/etc/bind/zones/db.192.168.22";
        allow-transfer { 192.168.106.20; };
        also-notify { 192.168.106.20; };
        notify yes;
};
```

Пояснення директив:
* `type master` — ця машина є джерелом даних зони (у BIND 9.16+ синонім — `type primary`).
* `allow-transfer` — кому дозволено AXFR. Дозволяємо тільки VM2.
* `also-notify` + `notify yes` — одразу надсилати NOTIFY на VM2 при зміні зони.

### 3.3. Файл прямої зони `color.edu`

```bash
sudo nano /etc/bind/zones/db.color.edu
```

```dns
$TTL    3600
$ORIGIN color.edu.
@       IN      SOA     ns1.color.edu. admin.color.edu. (
                        2026092001      ; Serial
                        3600            ; Refresh
                        900             ; Retry
                        604800          ; Expire
                        86400 )         ; Negative Cache TTL
;
; ----- Сервери імен зони -----
@       IN      NS      ns1.color.edu.
@       IN      NS      ns2.color.edu.
;
ns1     IN      A       192.168.106.10
ns2     IN      A       192.168.106.20
;
; ----- Ресурси зони (варіант 6) -----
red     IN      A       192.168.22.10
green   IN      A       192.168.22.20
blue    IN      A       192.168.22.30
black   IN      A       192.168.22.40
white   IN      A       192.168.22.50
;
; ----- Псевдоніми -----
ws1     IN      CNAME   red
ws2     IN      CNAME   green
ws3     IN      CNAME   blue
ws4     IN      CNAME   black
ws5     IN      CNAME   white
```

Що тут важливо:
* У SOA і NS імена **абсолютні** — з крапкою в кінці.
* `red`, `ws1` — **відносні**, до них додається `$ORIGIN`, тобто вийде `red.color.edu.`
* `ns1`/`ns2` мають A-записи всередині зони — це обов'язково, інакше NS-записи «висітимуть у повітрі».
* CNAME вказує на **ім'я**, не на адресу.

### 4.1. Опції

### 4.2. Опис зон як slave

```bash
sudo nano /etc/bind/named.conf.local
```

```conf
zone "color.edu" {
        type slave;
        file "/var/cache/bind/db.color.edu";
        masters { 192.168.106.10; };
        allow-notify { 192.168.106.10; };
        allow-transfer { none; };
};

zone "zone06.net" {
        type slave;
        file "/var/cache/bind/db.zone06.net";
        masters { 192.168.106.10; };
        allow-notify { 192.168.106.10; };
        allow-transfer { none; };
};

zone "22.168.192.in-addr.arpa" {
        type slave;
        file "/var/cache/bind/db.192.168.22";
        masters { 192.168.106.10; };
        allow-notify { 192.168.106.10; };
        allow-transfer { none; };
};
```

Важливо:
* **Жодних файлів зон на VM2 створювати не треба** — вони з'являться самі після передачі.
* Файли мають лежати у каталозі, куди `named` має право писати — `/var/cache/bind` (це і є `directory`). У `/etc/bind` писати не можна через AppArmor.
* У BIND 9.16+ можна писати `type secondary;` і `primaries { ... };` — синоніми.

## Крок 6. Типові помилки й діагностика

| Симптом | Причина / що робити |
|---|---|
| `SERVFAIL` на свою ж зону | Синтаксична помилка або зона не завантажилась. `named-checkzone`, потім `journalctl -u named` |
| Ім'я розгортається як `red.color.edu.color.edu` | Забута крапка в кінці абсолютного імені |
| Slave не отримує зону | Не збільшений serial; `allow-transfer` не дозволяє VM2; фаєрвол блокує **TCP/53**; slave не має прав писати в каталог |
| `dig` дає відповідь, але без прапорця `aa` | Відповідь із кешу рекурсивного сервера, а не з зони. Використовуй `+norecurse` |
| `REFUSED` | Запит поза `allow-query` / `allow-recursion` |
| Сервер слухає лише 127.0.0.1 | Не вказано адресу в `listen-on` |
| `permission denied` у логах при записі зони | Файл slave-зони поза `/var/cache/bind` (блокує AppArmor) |
| Все ламається після редагування | Повернути бекап `named.conf.options.bak` |

Корисне:

```bash
sudo rndc status                 # стан сервера, к-сть зон
sudo rndc reload                 # перечитати всі зони
sudo rndc retransfer color.edu   # (на VM2) примусово перезабрати зону
sudo rndc flush                  # очистити кеш
sudo tcpdump -i enp0s8 -n port 53   # подивитись сам обмін DNS (згодиться з ЛР1)
```

Дуже показово для звіту: запустити `tcpdump -i enp0s8 -n port 53` на VM1 і побачити, що звичайний запит іде по **UDP/53**, а AXFR — по **TCP/53**.

# ЧАСТИНА 3. ВІДПОВІДІ НА КОНТРОЛЬНІ ЗАПИТАННЯ

**4.1. Призначення та принципи роботи DNS.**
DNS — розподілена ієрархічна база даних для перетворення доменних імен в IP-адреси та навпаки, а також для зберігання іншої інформації про домен (MX, TXT, SRV). Принципи: ієрархічний простір імен у вигляді дерева; делегування відповідальності за частини простору (зони) окремим серверам; резервування (кілька NS на зону); кешування результатів на час TTL. Працює поверх UDP/53 (звичайні запити) і TCP/53 (передача зон, великі відповіді).

**4.2. Типи DNS-серверів та їх призначення.**
Авторитетні (первинний — зберігає редагований файл зони; резервний — отримує копію через transfer, підвищує надійність і розподіляє навантаження); кешуючі/рекурсивні резолвери (обслуговують клієнтів, обходять ієрархію, кешують); перенаправляючі (forwarding) — пересилають запити вищому серверу; кореневі — знають делегування доменів верхнього рівня.

**4.3. Типи ресурсних записів та їх призначення.**
SOA — параметри зони й адміністративна інформація; NS — авторитетні сервери зони та делегування; A/AAAA — ім'я → IPv4/IPv6; CNAME — псевдонім, що вказує на канонічне ім'я; PTR — адреса → ім'я (зворотна зона); MX — поштові сервери з пріоритетом; TXT — довільний текст (SPF, DKIM); SRV — розташування служби (порт, пріоритет, вага).

**4.4. Робота сервера в ітеративному та рекурсивному режимах.**
У рекурсивному режимі сервер бере на себе повний пошук відповіді: послідовно опитує кореневий сервер, сервер TLD, авторитетний сервер зони — і повертає клієнту остаточний результат. В ітеративному режимі сервер віддає лише те, що знає сам: або відповідь, або посилання (referral) на сервери наступного рівня, і подальший пошук виконує сам клієнт. Авторитетні сервери зазвичай працюють ітеративно, резолвери — рекурсивно.

**4.5. Загальна процедура перетворення доменного імені в IP-адресу.**
Див. п. 1.5: застосунок → stub-resolver (перевірка `/etc/hosts` і кешу) → рекурсивний запит до сервера з `/etc/resolv.conf` → перевірка кешу → ітеративні запити до кореня, TLD і авторитетного сервера → авторитетна відповідь → кешування на час TTL → повернення клієнту.

**4.6. Кешування в DNS.**
Резолвери зберігають отримані записи протягом часу TTL, вказаного власником зони. Це зменшує затримку відповіді й навантаження на авторитетні сервери та кореневу інфраструктуру. Платою є затримка поширення змін — тому перед запланованою зміною запису TTL заздалегідь зменшують. Кешуються й негативні відповіді (NXDOMAIN) на час, заданий полем Minimum у SOA.
