# ЧАСТИНА 1. ТЕОРІЯ

## 1.1. Навіщо окремий протокол для файлів

HTTP теж вміє віддавати файли, але FTP (File Transfer Protocol, **RFC 959**, 1985 рік) — спеціалізований протокол саме для передачі файлів: навігація по каталогах, завантаження і вивантаження, різні типи даних (текст/бінарні), відновлення перерваної передачі, керування правами доступу через автентифікацію. Він старіший за HTTP і досі широко використовується для адміністрування серверів, хостингу, резервного копіювання.

## 1.2. Головна особливість FTP: два окремих з'єднання

Це **найважливіша концептуальна відмінність** FTP від більшості інших протоколів (HTTP, SMTP), які обходяться одним TCP-з'єднанням. У FTP їх **два**:

```
Клієнт                                   Сервер
  │                                          │
  │── Керуюче з'єднання (control) ─────────►│  TCP порт 21
  │     команди: USER, PASS, LIST, RETR...  │  (живе всю сесію)
  │                                          │
  │── Канал даних (data) ───────────────────│  TCP порт 20 (активний)
  │     сам вміст файлу / список каталогу    │  або довільний (пасивний)
  │                                          │  (відкривається заново на кожну передачу)
```

* **Керуюче з'єднання (control connection)** — відкривається один раз на початку сесії, на **порт 21** сервера, і живе, поки клієнт не відключиться. Через нього йдуть лише текстові команди й коди відповідей — ніякого вмісту файлів.
* **З'єднання даних (data connection)** — окреме TCP-з'єднання, яке відкривається **заново для кожної операції**, що передає дані: список файлів (`LIST`), завантаження (`RETR`), вивантаження (`STOR`). Після передачі з'єднання даних закривається, а керуюче лишається відкритим.

Саме через цю двоканальність FTP погано "дружить" із NAT і файрволами (невідомо заздалегідь, який порт відкриється для даних) — звідси й з'явились активний/пасивний режими (п. 1.4).

## 1.3. Команди та коди відповідей FTP

### Основні команди (ідуть через керуюче з'єднання)

| Команда | Призначення |
|---|---|
| `USER ім'я` | вказати ім'я користувача |
| `PASS пароль` | вказати пароль |
| `SYST` | запитати тип операційної системи сервера |
| `PWD` | показати поточний каталог |
| `CWD каталог` | перейти в інший каталог (change working directory) |
| `CDUP` | піднятись на рівень вище |
| `TYPE A` / `TYPE I` | тип передачі: `A` — ASCII (текст), `I` — Image/Binary (двійкові дані) |
| `PASV` | перейти в **пасивний** режим — попросити сервер відкрити порт і повідомити його номер |
| `PORT` | перейти в **активний** режим — клієнт сам повідомляє серверу, на яку адресу й порт підключатись |
| `LIST` / `NLST` | отримати список файлів поточного каталогу (через канал даних) |
| `RETR файл` | завантажити файл із сервера (download) |
| `STOR файл` | вивантажити файл на сервер (upload) |
| `DELE файл` | видалити файл |
| `MKD` / `RMD` | створити / видалити каталог |
| `RNFR` / `RNTO` | перейменувати файл (from / to) |
| `QUIT` | завершити сесію |

### Коди відповідей (та сама логіка, що й у SMTP — перша цифра визначає клас)

| Код | Значення |
|---|---|
| `220` | вітання сервера при підключенні |
| `331` | ім'я користувача прийнято, потрібен пароль |
| `230` | успішний логін |
| `150` | сервер відкриває канал даних, починає передачу |
| `226` | передача завершена успішно |
| `227` | відповідь на `PASV`: `Entering Passive Mode (h1,h2,h3,h4,p1,p2)` |
| `425` | не вдалось відкрити канал даних |
| `530` | не авторизовано (невірний логін/пароль, або анонімний доступ заборонено) |
| `550` | дія не виконана (немає файлу, немає прав) |

## 1.4. Активний та пасивний режими

Це про те, **хто ініціює TCP-з'єднання каналу даних**.

### Активний режим (`PORT`)

```
Клієнт                                            Сервер
  │ control: PORT 192,168,106,5,200,10 ─────────►│   (клієнт каже: "з'єднуйся на мою адресу, порт 51210")
  │                                                 │
  │ ◄──────── сервер САМ підключається ───────────│   з порту 20 на вказаний клієнтом порт
```

Клієнт командою `PORT` повідомляє серверу свою IP-адресу й номер порту, на якому він чекає з'єднання. Сервер сам ініціює TCP-з'єднання **з порту 20** на цей порт клієнта. Проблема: якщо клієнт за NAT/файрволом, вхідне з'єднання ззовні, яке ніхто не чекав, зазвичай блокується — активний режим у сучасних мережах майже не працює без спеціальних налаштувань.

### Пасивний режим (`PASV`) — сучасний стандарт

```
Клієнт                                            Сервер
  │ control: PASV ───────────────────────────────►│
  │ ◄──── 227 Entering Passive Mode (...,p1,p2) ──│   (сервер каже: "з'єднуйся на мене, порт X")
  │                                                 │
  │ ── клієнт САМ підключається ──────────────────►│   на вказаний сервером порт
```

Клієнт командою `PASV` просить сервер самому відкрити порт для даних. Сервер відповідає кодом `227` і номером порту (закодованим як два числа `p1,p2`, де реальний порт = `p1*256 + p2`). Після цього **клієнт сам** підключається до сервера на цей порт — тобто обидва TCP-з'єднання (і керуюче, і дані) ініціює клієнт, а значить вони однаково легко проходять крізь NAT/файрвол клієнта. Тому пасивний режим і став стандартом де-факто. Зворотна сторона: сервер має тримати відкритим діапазон портів для даних (`pasv_min_port`/`pasv_max_port` у vsftpd) — саме це налаштовуємо в Кроці 3.

## 1.5. FTPS і SFTP — дві різні речі з подібною назвою

Це питання контрольних 3.4 і 3.5, і їх часто плутають:

* **FTPS (FTP over SSL/TLS)** — це **той самий протокол FTP**, тільки керуюче й/або з'єднання даних загорнуті в TLS (аналогічно до STARTTLS/implicit TLS у пошті з ЛР3). Є два варіанти:
  * **Implicit FTPS** — TLS встановлюється одразу, окремий порт **990**.
  * **Explicit FTPS (FTPES)** — з'єднання починається як звичайний FTP на порту 21, а потім командою `AUTH TLS` переходить у шифрований режим (аналог `STARTTLS`).
  Зберігається вся "дволінійна" природа FTP (окремий канал даних), просто обидва канали можуть бути зашифровані.

* **SFTP (SSH File Transfer Protocol)** — це **зовсім інший протокол**, що не має нічого спільного з FTP, окрім частини назви. Це підсистема протоколу **SSH** (працює поверх **одного** TCP-з'єднання, порт **22**, той самий, що й звичайний SSH-логін). Всі команди й дані йдуть через єдиний зашифрований канал SSH — жодного окремого каналу даних, жодних проблем з NAT/файрволами, жодних портів 20/21 узагалі.

| | FTP | FTPS | SFTP |
|---|---|---|---|
| Базовий протокол | свій, RFC 959 | FTP + TLS | підсистема SSH |
| Порти | 21 (+ дані) | 21 або 990 (+ дані) | 22 (один) |
| Шифрування | немає | є (TLS) | є (SSH) |
| Кількість TCP-з'єднань | 2 (control + data) | 2 | 1 |
| Проблеми з NAT | так (вирішуються PASV) | так само | немає |

## 1.6. Анонімний доступ

Більшість FTP-серверів підтримують вхід під спеціальним ім'ям **`anonymous`** (або `ftp`) без реального пароля — за традицією як пароль просять ввести email-адресу (яку сервер ніяк не перевіряє). Анонімний користувач мапиться на окремий системний обліковий запис (`ftp`), і його права на файлову систему **повністю визначаються правами доступу каталогів/файлів на диску** — сервер лише вирішує, пускати такого користувача взагалі чи ні (`anonymous_enable`).

Типова структура анонімної частини сервера:
* `pub/` — "публічна" тека, **тільки читання** — сюди викладають файли для всіх охочих забрати.
* `incoming/` — тека **для завантаження**, часто з обмеженим читанням (щоб хтось не вивантажив нелегальний контент і одразу не роздавав його іншим) — у завданні прямо сказано "читання і запис", тому зробимо обидва права.

## 1.7. vsftpd — загальна ідея

**vsftpd** ("very secure FTP daemon") — один з найпоширеніших FTP-серверів на Linux, спроєктований з акцентом на безпеку (мінімум коду з правами root, стійка ізоляція процесів). Головний конфіг — один файл `/etc/vsftpd.conf`, де все налаштовується директивами `параметр=значення`. На відміну від Postfix/Dovecot із ЛР3, тут немає розділення на кілька файлів для різних аспектів — усе зосереджено в одному місці, плюс опціонально — **окремі конфіги для конкретних користувачів** (`user_config_dir`), якими ми й скористаємось, бо в нашому варіанті різні користувачі мають **різні** права (дехто лише R, дехто RW, дехто обмежений домашнім каталогом, дехто має доступ до всього дерева).

# ЧАСТИНА 2. ПОКРОКОВЕ ВИКОНАННЯ (варіант 6)

## Крок 0. План дій

1. Встановити vsftpd на VM1.
2. Створити системних користувачів `red/green/blue/black/white` з паролями.
3. Налаштувати анонімний доступ: `pub` (R) та `incoming` (RW).
4. Налаштувати обмеження доступу (chroot — "тільки домашній каталог" проти "все дерево") через `chroot_list`.
5. Налаштувати права запису (R проти RW) через окремі конфіги користувачів (`user_config_dir`).
6. Налаштувати пасивний режим (діапазон портів).
7. Перевірити все: `ftp`, `lftp`, вручну через `telnet`/`netcat`, подивитись трафік `tcpdump`.

## Крок 2. Створення системних користувачів (варіант 6)

```bash
sudo useradd -m -s /usr/sbin/nologin red
sudo useradd -m -s /usr/sbin/nologin green
sudo useradd -m -s /usr/sbin/nologin blue
sudo useradd -m -s /usr/sbin/nologin black
sudo useradd -m -s /usr/sbin/nologin white

sudo passwd red
sudo passwd green
sudo passwd blue
sudo passwd black
sudo passwd white
```

| Прапорець | Що означає |
|---|---|
| `-m` | створити домашній каталог (`/home/red` тощо) — саме туди й потраплятиме користувач після логіну по FTP |
| `-s /usr/sbin/nologin` | заборонити вхід через SSH/консоль — ці акаунти потрібні лише для FTP-автентифікації, а не для повноцінної роботи в системі |

> На відміну від ЛР3 (де ми переходили на віртуальних користувачів Dovecot), тут завдання прямо каже "створені користувачі" без уточнення формату — vsftpd найпростіше й найстандартніше працює саме **з реальними системними користувачами** (PAM-автентифікація через `/etc/shadow`), тому лишаємо `useradd`.

Для наочності покладемо в домашній каталог кожного по тестовому файлу — знадобиться для перевірки прав у Кроці 7:

```bash
for u in red green blue black white; do
  echo "Це файл користувача $u" | sudo tee /home/$u/hello.txt
  sudo chown $u:$u /home/$u/hello.txt
done
```

## Крок 3. Базова конфігурація vsftpd

```bash
sudo nano /etc/vsftpd.conf
```

Приводимо файл до такого вигляду (коментарі `#` можна лишити, нижче йде лише суть):

```conf
# ---------- Базові параметри ----------
listen=YES
listen_ipv6=NO

# ---------- Локальні (системні) користувачі ----------
local_enable=YES
write_enable=YES
local_umask=022

# ---------- Анонімний доступ ----------
anonymous_enable=YES
anon_root=/srv/ftp
anon_upload_enable=YES
anon_mkdir_write_enable=YES
anon_other_write_enable=YES
no_anon_password=YES

# ---------- Обмеження локальних користувачів домашнім каталогом ----------
chroot_local_user=YES
chroot_list_enable=YES
chroot_list_file=/etc/vsftpd.chroot_list
allow_writeable_chroot=YES

# ---------- Персональні налаштування по користувачах ----------
user_config_dir=/etc/vsftpd_user_conf

# ---------- Пасивний режим ----------
pasv_enable=YES
pasv_min_port=40000
pasv_max_port=40100
pasv_address=192.168.106.10

# ---------- Інформаційні банери та логи ----------
ftpd_banner=Welcome to ftp.color.edu FTP service.
xferlog_enable=YES
xferlog_file=/var/log/vsftpd.log
log_ftp_protocol=YES

# ---------- Безпека ----------
seccomp_sandbox=NO
```

Розбір кожного параметра:

| Параметр | Що означає |
|---|---|
| `listen=YES` | запускати vsftpd як самостійний демон на IPv4 (а не через inetd/xinetd — старий спосіб) |
| `listen_ipv6=NO` | не слухати IPv6 — у нас лабораторія суто IPv4 |
| `local_enable=YES` | дозволити вхід **системним** користувачам Linux (без цього працював би тільки анонімний доступ) |
| `write_enable=YES` | **глобально** дозволити будь-які команди запису (`STOR`, `DELE`, `MKD`...). Це "рубильник" верхнього рівня — без нього запис неможливий взагалі ні для кого, навіть якщо нижче дозволити окремому користувачу |
| `local_umask=022` | маска прав для нових файлів, які створюють локальні користувачі (стандартне значення: файли `644`, каталоги `755`) |
| `anonymous_enable=YES` | дозволити вхід під `anonymous`/`ftp` |
| `anon_root=/srv/ftp` | корінь файлової системи для анонімного користувача — де лежатимуть `pub/` і `incoming/` |
| `anon_upload_enable=YES` | дозволити анонімному користувачу вивантажувати файли (потрібно для `incoming`) |
| `anon_mkdir_write_enable=YES` | дозволити анонімному користувачу створювати каталоги |
| `anon_other_write_enable=YES` | дозволити інші операції запису — перейменування, видалення (без цього параметра анонім міг би тільки вивантажувати, але не видаляти/перейменовувати) |
| `no_anon_password=YES` | не питати пароль у анонімного користувача взагалі (спрощує лабораторну; стандартна поведінка — приймати будь-який рядок як "пароль", тут іще простіше) |
| `chroot_local_user=YES` | **за замовчуванням обмежити кожного локального користувача його домашнім каталогом** (т.зв. chroot-в'язниця — користувач фізично не може командою `CWD ..` вийти за межі `/home/<ім'я>`) |
| `chroot_list_enable=YES` + `chroot_list_file=...` | увімкнути **виняток** із щойно встановленого правила: користувачі, перелічені у вказаному файлі, навпаки, **НЕ будуть обмежені** (отримають доступ до "всього дерева каталогів") — саме так реалізуємо різницю `green`/`white` проти `red`/`blue`/`black` |
| `allow_writeable_chroot=YES` | vsftpd новіших версій відмовляється chroot'ити користувача, якщо той має право писати у свій же корінь (із міркувань безпеки); цей параметр явно дозволяє таку комбінацію — без нього `blue` (chroot + RW у власному домашньому каталозі) не зможе залогінитись |
| `user_config_dir=/etc/vsftpd_user_conf` | тека, де для **кожного окремого користувача** можна покласти файл з його іменем і перевизначити будь-який параметр `main.conf` — саме тут налаштуємо персональні права R/RW (Крок 5) |
| `pasv_enable=YES` | увімкнути підтримку пасивного режиму (п. 1.4 теорії) |
| `pasv_min_port` / `pasv_max_port` | діапазон портів, які сервер пропонуватиме клієнтам для каналу даних у пасивному режимі — вузький діапазон зручно явно дозволити у файрволі |
| `pasv_address` | яку IP-адресу повідомляти клієнту у відповіді на `PASV` (критично, якщо сервер має кілька мереж — наш VM1 підключений і до NAT, і до VNet1; явно вказуємо адресу з лабораторної мережі) |
| `ftpd_banner` | текст привітання при підключенні (видно в будь-якому клієнті одразу після з'єднання) |
| `xferlog_enable` + `xferlog_file` | вести лог усіх передач файлів — знадобиться для аналізу (Крок 7) |
| `log_ftp_protocol=YES` | писати в лог **увесь** протокольний обмін командами (не лише факт передачі файлу) — саме це потрібно для п. 2.2 завдання ("аналіз протокольного обміну") |
| `seccomp_sandbox=NO` | вимикає додаткову пісочницю ядра (seccomp), яка в деяких контейнерах/віртуалках заважає vsftpd запуститись — якщо у вас усе працює і без цього рядка, можна прибрати |

## Крок 4. Хто обмежений домашнім каталогом, а хто має доступ до всього дерева

Згідно з `chroot_local_user=YES` із Кроку 3, **усі** локальні користувачі за замовчуванням обмежені домашнім каталогом. Файл `chroot_list_file` — це список **винятків**, тобто тих, хто, навпаки, отримає повний доступ.

За варіантом 6 повний доступ ("до всього дерева каталогів") мають **`green`** і **`white`**.

```bash
sudo nano /etc/vsftpd.chroot_list
```

```
green
white
```

Просто по одному імені в рядку. Решта (`red`, `blue`, `black`) у файл не потрапляють — лишаються "в'язнями" власного домашнього каталогу.

> **Важливо для звіту:** варто явно показати різницю командою `cd /` або `cd /etc` під час FTP-сесії: у `red` вона поверне `550 Failed to change directory` (бо вище власного домашнього каталогу "нічого немає" — chroot фізично підмінює корінь файлової системи), а в `green` — спрацює і покаже реальний вміст `/etc` системи.

## Крок 5. Персональні права кожного користувача (R проти RW)

Глобально ми вже дозволили запис (`write_enable=YES` у Кроці 3) — інакше не змогли б писати навіть ті, кому положено. Тепер для користувачів, яким за варіантом покладено **тільки читання** (`red`, `black`), створюємо персональний конфіг, що **забирає** право запису особисто для них.

```bash
sudo mkdir -p /etc/vsftpd_user_conf
```

```bash
sudo nano /etc/vsftpd_user_conf/red
```
```conf
write_enable=NO
```

```bash
sudo nano /etc/vsftpd_user_conf/black
```
```conf
write_enable=NO
```

Користувачам з правом RW (`green`, `blue`, `white`) окремий файл не обов'язковий (їм підходить глобальне `write_enable=YES` без змін), але для наочності й повноти звіту краще завести порожні/явні файли:

```bash
sudo nano /etc/vsftpd_user_conf/green
```
```conf
write_enable=YES
```

```bash
sudo nano /etc/vsftpd_user_conf/blue
```
```conf
write_enable=YES
```

```bash
sudo nano /etc/vsftpd_user_conf/white
```
```conf
write_enable=YES
```

**Як це працює механічно:** при вході користувача `red` vsftpd спочатку застосовує `/etc/vsftpd.conf`, а потім, якщо в `user_config_dir` існує файл з іменем, що точно збігається з логіном (`/etc/vsftpd_user_conf/red`), **довантажує** його поверх — і будь-який параметр у цьому файлі **перевизначає** глобальне значення саме для цього користувача, не чіпаючи інших.

Підсумкова таблиця того, що вийшло (звір із завданням варіанту 6):

| Користувач | `chroot_list` (повний доступ)? | `write_enable` персонально | Підсумок |
|---|---|---|---|
| `red` | ні → chroot (тільки домашній) | `NO` | тільки домашній каталог, R |
| `green` | так → без chroot (все дерево) | `YES` | все дерево, RW |
| `blue` | ні → chroot (тільки домашній) | `YES` | тільки домашній каталог, RW |
| `black` | ні → chroot (тільки домашній) | `NO` | тільки домашній каталог, R |
| `white` | так → без chroot (все дерево) | `YES` | все дерево, RW |

## Крок 6. Анонімний доступ: `pub` та `incoming`

```bash
sudo mkdir -p /srv/ftp/pub /srv/ftp/incoming
```

### Корінь анонімної зони

```bash
sudo chown root:root /srv/ftp
sudo chmod 555 /srv/ftp
```

`555` — читання й виконання (прохід) для всіх, без запису навіть у сам корінь: анонім не повинен створювати файли прямо в `/srv/ftp`, лише всередині `pub`/`incoming`.

### `pub` — тільки читання

```bash
sudo chown root:root /srv/ftp/pub
sudo chmod 555 /srv/ftp/pub
echo "Публічний файл для прикладу" | sudo tee /srv/ftp/pub/readme.txt
sudo chmod 444 /srv/ftp/pub/readme.txt
```

`555` на каталозі — можна заходити й переглядати список, `444` на файлі — можна лише читати, записати чи видалити — ні в кого, крім root.

### `incoming` — читання і запис

```bash
sudo chown ftp:ftp /srv/ftp/incoming
sudo chmod 777 /srv/ftp/incoming
```

| Частина | Що означає |
|---|---|
| `chown ftp:ftp` | власником робимо того самого системного користувача, під яким vsftpd виконує операції анонімного доступу (стандартний акаунт `ftp`, створюється автоматично під час встановлення пакета) |
| `chmod 777` | повні права читання/запису/виконання для всіх — у реальному проді так ніколи не роблять (будь-хто б міг завантажити що завгодно і роздавати), але завдання прямо вимагає "читання та запис" для `incoming`, тому в лабораторній це свідомий і очікуваний результат |

Перевірка власника самого процесу (яким користувачем анонім "представлений" у системі):

```bash
grep ftp /etc/passwd
```

## Крок 7. Перезапуск і перевірка синтаксису

```bash
sudo vsftpd -olisten=NO /etc/vsftpd.conf &  # швидкий тест конфіга без запуску служби (Ctrl+C щоб зупинити)
```

Основний спосіб перевірки — просто перезапустити службу й подивитись, чи не впала:

```bash
sudo systemctl restart vsftpd
sudo systemctl status vsftpd
sudo ss -lnptu | grep :21
journalctl -u vsftpd -n 30 --no-pager
```

Якщо на етапі логіну `blue` (chroot + write) з'являється помилка на кшталт `500 OOPS: vsftpd: refusing to run with writable root inside chroot()` — значить забули `allow_writeable_chroot=YES` з Кроку 3, або домашній каталог користувача (сам `/home/blue`) має права запису для групи/інших — тоді потрібно прибрати зайві права:

```bash
sudo chmod 755 /home/blue
```

## Крок 8. Перевірка роботи

### 8.1. Базовий вхід через `ftp`

```bash
ftp 192.168.106.10
```

```
Name: red
Password: ********
ftp> pwd
ftp> ls
ftp> get hello.txt
ftp> cd /          <- для red має бути відмовлено (chroot)
ftp> put test.txt  <- для red має бути відмовлено (тільки R)
ftp> quit
```

Повторити для `green` — і `cd /`, і `put` мають спрацювати.

### 8.2. Через `lftp` (рекомендований клієнт завдання, зручніший і детальніший вивід)

```bash
lftp -u blue, 192.168.106.10
```

```
lftp blue@192.168.106.10:~> ls
lftp blue@192.168.106.10:~> put /etc/hostname -o myfile.txt
lftp blue@192.168.106.10:~> cd /etc        # має бути відмовлено — blue в chroot
lftp blue@192.168.106.10:~> bye
```

`lftp` одразу працює в пасивному режимі за замовчуванням, і має зручну команду `debug` для показу повного протокольного обміну:

```bash
lftp -u white, 192.168.106.10 -e "debug 3; ls; cd /; ls; bye"
```

`debug 3` виводить **усі** команди й коди відповідей прямо в консоль — найзручніший спосіб зняти "протокольний обмін" для звіту (п. 2.2 завдання) без окремого `tcpdump`.

### 8.3. Анонімний доступ

```bash
ftp 192.168.106.10
```
```
Name: anonymous
Password: anything@anything
ftp> cd pub
ftp> get readme.txt
ftp> put test.txt      <- має бути відмовлено (pub лише читання)
ftp> cd ../incoming
ftp> put test.txt       <- має спрацювати
ftp> ls                 <- перевірити, що файл з'явився
ftp> quit
```

### 8.4. Вручну через `telnet` — лише керуюче з'єднання (найкраще для аналізу команд)

```bash
telnet 192.168.106.10 21
```

```
220 Welcome to ftp.color.edu FTP service.
USER red
331 Please specify the password.
PASS ********
230 Login successful.
SYST
215 UNIX Type: L8
PWD
257 "/" is the current directory
QUIT
221 Goodbye.
```

Через `telnet` можна ввести лише команди керуючого каналу — `LIST`/`RETR`/`STOR` не спрацюють повноцінно, бо для них потрібен ще й канал даних, який telnet окремо не відкриє. Саме тому для повної демонстрації краще `ftp`/`lftp`, а `telnet` — щоб показати "сирий" текстовий діалог автентифікації (аналогічно до того, що робили з SMTP у ЛР3).

### 8.5. `netcat` — перевірити, що порт слухає, і отримати банер

```bash
nc -v 192.168.106.10 21
```

Одразу після з'єднання сервер сам надсилає `220 ...` — так само, як `telnet`, тільки простіше для швидкої перевірки "чи взагалі сервер живий".

### 8.6. Аналіз трафіку (tcpdump) — побачити, як саме влаштоване з'єднання даних

```bash
sudo tcpdump -i lo -n port 21 or portrange 40000-40100 -A
```

Під час виконання `ls`/`get`/`put` у іншому терміналі видно:
1. Спершу обмін командами на порту **21** (включно з `PASV` і відповіддю `227 Entering Passive Mode (192,168,106,10,156,32)` — останні два числа кодують номер порту даних: `156*256+32 = 40000`).
2. Потім **окреме** TCP-з'єднання на порт із діапазону `40000–40100` — саме канал даних, яким і передається вміст файлу чи список каталогу.

Це найнаочніша демонстрація того, чому FTP називають "дволінійним" протоколом (п. 1.2 теорії) — у логах видно два незалежні TCP-потоки з різними портами.

### 8.7. Перегляд логу сервера

```bash
sudo tail -40 /var/log/vsftpd.log
```

Там видно кожен логін, кожну команду (завдяки `log_ftp_protocol=YES`) і кожну передачу файлу з розміром і часом — готовий матеріал для звіту без ручного набору команд.

## Крок 9. Типові проблеми

| Симптом | Причина / що робити |
|---|---|
| `500 OOPS: vsftpd: refusing to run with writable root inside chroot()` | домашній каталог користувача, якого chroot'имо, має права запису для group/other — прибрати (`chmod 755 /home/user`), або додати `allow_writeable_chroot=YES` |
| `530 Login incorrect` | невірний пароль, або користувача взагалі немає в `/etc/passwd`/`/etc/shadow` |
| `530 This FTP server is anonymous only` | `local_enable` виключено або не застосувалось — перевір `vsftpd.conf` і перезапусти службу |
| Пасивний режим "висить", дані не йдуть | `pasv_address` вказує не ту адресу (наприклад, адресу NAT-інтерфейсу замість VNet1), або файрвол блокує діапазон `pasv_min_port–pasv_max_port` |
| Користувач з `write_enable=NO` все одно може писати | перевір, що файл дійсно лежить у `/etc/vsftpd_user_conf/<точне ім'я>` і що `user_config_dir` прописано в головному конфізі — і перезапусти vsftpd |
| `green`/`white` не отримують доступ до всього дерева | перевір, що ім'я в `/etc/vsftpd.chroot_list` написане **без** помилок, і що `chroot_list_enable=YES` |
| Анонім не може вивантажити в `incoming` | перевір `anon_upload_enable=YES`, права на `incoming` (`777`, власник `ftp`) |

# ЧАСТИНА 3. ВІДПОВІДІ НА КОНТРОЛЬНІ ЗАПИТАННЯ

**3.1. Протокол FTP: призначення та особливості роботи.**
FTP (RFC 959) — протокол для передачі файлів між клієнтом і сервером поверх TCP. Головна особливість — використання **двох окремих TCP-з'єднань**: керуючого (control, порт 21), яким передаються лише текстові команди й коди відповідей, і каналу даних (data), що відкривається окремо для кожної операції передачі (список каталогу, завантаження, вивантаження) і закривається після її завершення. Підтримує автентифікацію (у т.ч. анонімний доступ), навігацію по каталогах, два типи передачі даних (текстовий ASCII і двійковий Binary).

**3.2. Пасивний та активний режими роботи FTP-сервера.**
Різняться тим, хто ініціює TCP-з'єднання каналу даних. В **активному режимі** (команда `PORT`) клієнт повідомляє серверу свою адресу й порт, і сервер сам підключається до клієнта з порту 20 — погано працює через NAT/файрволи клієнта. У **пасивному режимі** (команда `PASV`) сервер відкриває порт і повідомляє його клієнту (код `227`), після чого клієнт сам підключається до сервера — обидва з'єднання ініціює клієнт, тому пасивний режим є сучасним стандартом і легко проходить крізь NAT.

**3.3. Команди протоколу FTP.**
Автентифікація: `USER`, `PASS`. Навігація: `PWD`, `CWD`, `CDUP`. Налаштування передачі: `TYPE`, `PASV`, `PORT`. Робота з файлами: `LIST`/`NLST` (список), `RETR` (завантажити з сервера), `STOR` (вивантажити на сервер), `DELE` (видалити), `MKD`/`RMD` (каталоги), `RNFR`/`RNTO` (перейменування). Завершення сесії: `QUIT`. Кожна команда отримує текстову відповідь із трицифровим кодом (2xx — успіх, 3xx — потрібне продовження, 4xx/5xx — помилка).

**3.4. Протокол FTPS (FTP зверху SSL/TLS).**
FTPS — це звичайний протокол FTP із доданим шифруванням TLS, при цьому зберігається оригінальна дволінійна архітектура (окремі канал команд і канал даних). Є два варіанти: **implicit FTPS** — TLS встановлюється одразу при з'єднанні на окремому порту (990), і **explicit FTPS** — з'єднання починається як звичайний FTP на порту 21, а перехід у шифрований режим відбувається командою `AUTH TLS` (аналог `STARTTLS` у SMTP). FTPS складний для роботи через NAT, бо й керуючий, і канал даних потребують окремого шифрування і узгодження портів.

**3.5. Протокол SFTP.**
SFTP (SSH File Transfer Protocol) — протокол передачі файлів, що є підсистемою **SSH** і не має спільного походження з FTP, попри схожу назву. Працює поверх **одного** зашифрованого TCP-з'єднання (порт 22, той самий, що й звичайний SSH), тому не має проблем FTP з окремим каналом даних і NAT. Автентифікація — стандартні механізми SSH (пароль або ключова пара). Через простішу мережеву модель і вбудоване шифрування SFTP у сучасних системах зазвичай витісняє звичайний FTP і FTPS там, де потрібна безпечна передача файлів.
